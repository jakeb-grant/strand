# The Strand language specification

Status: **skeleton** (M5 wave 1, S-docs). The section list, the
construct index and the compatibility policy's wording are fixed here
first, so the tree-sitter grammar (S-lsp, wave 2) and the guide can be
built against them; each section's normative text follows on the same
branch. A section that still reads "Text to come" states nothing yet;
until it is written, `docs/design.md` decides that section's meaning.

## 1. Scope and status

- This file says what a `.strand` program **means**. `docs/grammar.md`
  says how it is **written**: every production, the lexical rules, line
  termination and error recovery. Together the two are the frozen
  language (decisions.md m5-owner, Q5).
- spec.md is self-contained. Its text is copied from design.md and
  adapted, never linked to it, so a later edit to design.md's rationale
  cannot change frozen behaviour. Where design.md is silent, the rules
  come from architecture.md and decisions.md and are restated here.
- spec.md adds no syntax. Every construct it names is a production of
  grammar.md (index in section 3).
- Builtin elements, props, service fields and actions are not listed
  here; they are the builtin and service schemas, published as
  `docs/reference/` (generated by `strand-dev reference`). This file
  fixes the rules every schema entry obeys.

## 2. Conformance and terms

Text to come: "must", "never", "load error", "warning", "lint",
"runtime fault"; a program is *accepted* when `strand check` reports no
error; what a diagnostic must carry (file, line, caret, label, fix);
diagnostic codes (`check::…`, `syntax::…`) are named for reference and
are not part of the frozen surface.

## 4. Programs and files

### 4.1 The module set

Text to come: every `.strand` file at most three directories below the
config directory is one module of one program; no imports, no entry
file; names starting with `.` skipped; symlinks followed, each file
claimed once at its shallowest path; top-level elements and props are
an error.

### 4.2 Names across files

Text to come: one namespace across files; redeclaration across files is
a load error naming both; `export` makes a value reachable as
`file.name` from the CLI and from other files; unknown names get a
did-you-mean.

## 5. Declarations

### 5.1 Surfaces

Text to come: `bar` is on every monitor that its `screens:` picks, with
`screen` in scope; `panel`, `osd` and `lock` defaults; `popup` is an
element anchored to its parent; surfaces hold state.

### 5.2 Components and slot

Text to come: one call shape; parameters by position and name, defaults,
inferred types; children render at `slot`; component `tokens { }`
exposes `$Name.token`; components hold state.

### 5.3 state, let and export

Text to come: `state` is writable, `let` is derived and read-only; where
each may appear (components, surfaces, list items; `let` in handlers
and `fn`s as a local); state never lives on leaf elements.

### 5.4 Enums and record types

Text to come.

### 5.5 Functions

Text to come: `fn`s are pure; the body's value is its last expression.

### 5.6 Custom services and permits

Text to come: `from dbus` checked against introspection; `from file`,
`from listen`, `from poll` checked against the declared schema;
running a command needs `permit exec`; a polled path reads the file.

## 14. Compatibility

In 1.x:

- no syntax is removed, and no syntax changes meaning;
- builtin schema entries (elements, props, service fields, actions) are
  only added, never removed or changed in meaning.

Anything else waits for 2.0. After the freeze, any change to
grammar.md or spec.md needs a decisions.md paragraph citing this
section; typo fixes are exempt. The freeze is held by this process and
by the conformance tests (the fixture tests, the tree-sitter conformance
test and the guide's ladder test), not by a hash pin.
