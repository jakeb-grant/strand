# The Strand language specification

Status: **frozen** (2026-10-12, the last commit of M5's wave 3;
decisions.md m5-integration-w3, "the language freeze"). The freeze
review settled every point the draft left open, each with a test
(decisions.md m5-docs, "the freeze review"); the last, equality across
units (7.2), with the checker change that landed in wave 3's sweep.
From the freeze this file and `docs/grammar.md` are the language 1.x
promises, and a change to either needs a decisions.md paragraph that
cites the compatibility policy (section 14); typo fixes are exempt. The theming hub (hue roles, the palette's extras and identity,
templates, the `file` element and `strand export`; sections 4.1, 9 and
13) is owner-approved design (decisions.md m5-tools), built in M5 wave 2
(decisions.md m5-palette, m5-tools); the text here follows the code as
built.

## 1. Scope and status

- This file says what a `.strand` program **means**. `docs/grammar.md`
  says how it is **written**: every production, the lexical rules, line
  termination and error recovery. Together the two are the frozen
  language (decisions.md m5-owner, Q5).
- spec.md is self-contained. Its text is copied from design.md and
  adapted, never linked to it, so a later edit to design.md's rationale
  cannot change frozen behaviour. Where design.md is silent, the rules
  come from architecture.md and decisions.md and are restated here.
- spec.md adds no syntax. Every construct it names is a production of
  grammar.md (index in section 3).
- Builtin elements, props, service fields, actions and functions are
  not listed here; they are the builtin and service schemas, published
  as `docs/reference/` (generated by `strand-dev reference`). This file
  fixes the rules every schema entry obeys.
- Numbers given as targets (latencies, memory) are not part of the
  language. Numbers that change what a program does (the 15 ms
  coalesce, the 250 ms overlay delay, the 250 ms settings write delay,
  30 writes per second, the 30 s monitor retention, the 4 px query
  hysteresis, the 5 s service stop, the 100 ms floor of a polled
  command) are.

## 2. Conformance and terms

- **must** and **never** are requirements on the implementation;
  **may** is a permission.
- A **load error** stops a program, or the changed set of files in a
  reload, from being committed. `strand check` reports it and exits with
  an error; a running shell keeps its last good tree (section 10.5).
- A **warning** is reported, and the program is committed. A **lint** is
  a warning about style.
- A **runtime fault** is an error while the program runs (section 12).
  Evaluation errors are values, never crashes.
- Every diagnostic carries its file, line and column, a caret under the
  span, a label, and a fix where one exists (a did-you-mean, the missing
  word). One mistake gives one diagnostic. Diagnostic codes
  (`syntax::…`, `check::…`) and message wording are named for reference
  and are **not** part of the frozen surface.
- A program is **accepted** when `strand check` reports no load error.

## 4. Programs and files

### 4.1 The module set

- A **config** is a directory: `$XDG_CONFIG_HOME/strand` by default, or
  the directory given to `strand run` or `strand check`.
- Every `.strand` file at most three directories below the config
  directory is one **module** of one program. Files and directories
  whose names start with `.` are skipped. Symbolic links are followed,
  and each file is one module however many paths reach it (it is claimed
  at its shallowest path). `strand check` warns about deeper directories
  that hold `.strand` files, since they are not loaded.
- There are no imports and no entry file. Every module is loaded.
- Elements and props at the top level of a file are a load error: they
  must be inside a surface or a component. The one exception is a
  `file` element (section 9.7), which draws nothing and may stand at the
  top level as well as in a tree.

### 4.2 Names across files

- **Global names** are shared by every module: components, surfaces,
  enums, types, `fn`s, token sets, keyframes, actions and services.
  Declaring a surface, service, token set, keyframes or action twice, in
  one file or two, is a load error naming both places; so is declaring
  any global name twice in one file, or a component, type, enum or `fn`
  under the name of one of those.
- **The same name in two files.** (M6, the owner's ruling) A component,
  type, enum or `fn` may be declared under one name in more than one
  file. A use resolves by three rules, counting only the declarations
  its position takes: a type position (`x: Item`) takes types and
  enums, an element takes components, a call (`f(x)`, `Item(a: 1)`)
  takes `fn`s and types, and a variant (`Kind.dark`, in a pattern too)
  takes enums. (1) A file that declares such a name uses its own
  declaration; (2) a file without its own uses the single declaration
  elsewhere, as when the name is unique; (3) where two or more other
  files declare it, a bare use is a load error at the use
  (`check::ambiguous_name`) that names every declaring file and offers
  `file.Name`. Where no declaration of the position's kind exists, the
  name means what it did without them (a builtin type, a schema enum):
  two `component Workspace`s do not hide the `Workspace` type, and a
  `type Item` in one file and a `component Item` in another are never
  ambiguous. A name declared once means that declaration wherever it is
  used, as before. **`file.Name`** names the declaration in `file`,
  wherever a bare name can stand: a component call (`menu.Row e { … }`),
  a type (`x: menu.Item?`, `menu.Item(a: 1)`), an enum and its variants
  (`menu.Kind.dark`, in a pattern too) and a `fn` call (`menu.fmt(x)`).
  It is the form exports already use, with the same rule: the file's
  name must be an identifier. Where a file's name is not one, the error
  and the note say to rename the file instead of offering `file.Name`;
  two files with one name in different directories (`bar/row.strand`,
  `menu/row.strand`) that both declare a shared name are a load error
  (`check::file_name`) asking to rename one, since `row.Name` could not
  say which. In an element and a type, `menu.Name` is the file's
  declaration whenever no local or file-level name `menu` is in scope,
  so a file named like a service, value or builtin type (`tray.strand`,
  `battery.strand`, `color.strand`) is named the same way; a local or
  file-level `menu` keeps its reading (in a tree, `n.expire()` stays a
  statement where `n` is a value). In an expression (a call, a
  constructor, a variant) a service, builtin value or enum called `menu`
  that has a member `Name` keeps that meaning (`battery.percent` is the
  service's field, `Edge.top` the builtin variant beside an
  `Edge.strand`), and the error and the note then ask to rename the file
  instead of offering it; a file's exported `state` or `let` of that
  name is read as before. `self` and the node names (`hover`, …) are
  never file qualifiers. `strand
  check` and the language server put a note (`check::same_name`, not an
  error or a warning) at each declaration of a name declared in more
  than one file, listing the other files; a load never reports it, and
  `strand check FILE` counts only the notes at that file's
  declarations. Messages, hover, completion, the inspector and live
  reload show such a component, type or enum as `file.Name`. A
  component's `tokens { }` keep its tokens under `$file.Name.…`; `$Row.gap`
  and a set's `override Row.gap` follow rules 1 and 2 over the
  components of that name with tokens (inside `a`'s `Row`, or anywhere
  in `a.strand`, it is `a`'s; elsewhere the only one with tokens), and
  where two or more other files' have tokens the read is an error
  offering `$a.Row.gap`. A template (section 9.8) reads tokens by their
  full path at run time, so it writes `$a.Row.gap`. Adding a second
  declaration can make a bare use in a third file an error; a live
  reload then keeps running the last program that loaded until the use
  is qualified. What a live reload keeps: when a name becomes shared or
  unique again, every component's cells (list items' included), its
  `persist` values (the path moves between `Row.open` and `a.Row.open`
  with the live value, and the old path is removed), settings fields,
  and values of the types; when a component moves to another file and
  its old file no longer declares that name (moved, or pasted into
  another file and then cut), the same, at each call that now names it;
  when a type or enum moves, its values and settings fields, if its name
  is unique before and after. Its limits: a shared type or enum moved to
  another file is a new type, so values of it start from their defaults; a call that comes to name another
  file's declaration while the one it named still exists (pasting a
  component into the file that calls it) starts that call's state from
  its defaults, as calling a different component does; and a `persist`
  value whose path changed form while strand was not running is moved on
  the next start only when that is unambiguous (while the name is
  shared, `Row.open` is not taken when another file's `Row` has an
  `open` too), stamped with the current default, so a "kept over the new
  default" notice is not shown on that start. Every program that loaded
  before resolves exactly as before (section 14).
- **File names.** A top-level `state` or `let` belongs to its file.
  Another file reads it as `file.name`, and only if it is declared
  `export`; a name that is another file's private declaration is a load
  error that names it and the `export` to add. A file whose exports are
  read must have a name that is an identifier (`my-bar.strand` is a load
  error once it exports), and a file named like a service cannot export
  (the name means the service).
- `export` also makes the value reachable from the command line as
  `file.name` (section 13).
- **Builtins are a prelude.** A `state`, `let`, parameter, `fn`,
  `type`, `enum` or component may shadow a builtin function or value,
  or a service schema's record or enum, within its scope. A `state` or
  `let` that hides a builtin service, or a builtin value such as the
  time signal `t`, is a warning; so is an `fn`, `type`, `enum` or
  component named like a builtin service. (M6, the owner's ruling) A
  config `service` named like a builtin service shadows it within the
  config, with the same warning: the config's own service is the one
  its reads, writes, actions, `on` handlers and `strand call` reach,
  and the builtin's fields and events are not there. The runtime's own
  reads (the default palette's `system` fields, the `screens` that
  mount bars, `system.reduced_motion`) still go to the builtin. So a
  config keeps loading when a release adds a builtin service of a name
  it uses (section 14). A config enum's variant does not hide a
  builtin: where no enum is expected, a bare name that is both a
  builtin service or value and a variant (`state module = network`
  beside `enum Module { network, battery }`) reads the builtin, and
  that use is a warning naming the variant and its enum, which
  `Module.network` writes. Where the enum is expected (`module =
  battery`, `kind == volume` with `kind` a `Kind`) the variant is read,
  and a field read (`network.ssid`) is the service's. A file's `state` or
  `let` named like a node boolean (`hover`, `pressed`, `focused`,
  `selected`, section 6.3) is a warning too: inside an element the bare
  name is that element's boolean and outside one it names none, so it
  never reads the declaration, and each bare use where the file declares
  it warns that it read the node's (decisions.md
  builtin-name-diagnostics). A parameter, `for` binding or handler `let`
  of such a name is read before the node's and is not hidden.
- **Some builtin names are taken.** Two declarations are load errors
  rather than shadows: a `type` or `enum` named like one of the
  language's own types (`bool`, `int`, `float`, `length`, `percent`,
  `angle`, `duration`, `color`, `paint`, `text`, `path`, `font`,
  `shadow`, `insets`, `corners`, `any`, `unit`, `Async`); and a
  `component` or surface named like a builtin element (`text`, `row`,
  `popup`, …), since an element is resolved before a component.
  Palette role names, the 13 hue roles
  included, and the token first segment `palette` are taken too
  (section 9.3).
- **Shadowing is loud.** A name in scope that is also a variant of the
  enum a position expects is a load error (the reading would be
  ambiguous); so is a parameter declared again in its body, a file's
  `state` named like a component, and a handler `let` declared twice in
  one block. A prop set twice in one element or one `when` is a load
  error.
- An unknown name is a load error with a did-you-mean: the expected
  enum's variants first, keyframes for `play`, and other files' exports
  as `file.name`.

## 5. Declarations

### 5.1 Surfaces

A surface is something the compositor shows. Its body is a tree
(section 6). Every surface accepts `screens:`, `layer:`, `open:`,
`keyboard:`, `anchor:` and `inhibit_idle:`, and the events `on show`
and `on hide`, except that a `window` takes none of the props that
place a layer surface (below).
`attach:` and `scrim:` are accepted only on a `panel` (and on a
`popup`); on a `bar`, `osd` or `lock` either one is a load error. On a
`lock`, `layer:`, `anchor:` and `keyboard:` are warnings:
`ext-session-lock` decides all three (above everything, filling the
monitor, the keyboard always).

- **`bar Name { … }`** is on every monitor that its `screens:` picks
  (all of them by default). Each monitor gets its own instance, with the
  read-only `screen` (that monitor) in scope, and its own state. A
  monitor plugged in later gets an instance; an unplugged monitor's
  instance is parked with its state for 30 seconds and comes back with
  it if the monitor returns (monitors are matched by make, model and
  description). A `Screen` says where the monitor is in the
  compositor's layout (`x`, `y`, logical pixels, as `width` and
  `height`), and `screens.all` lists the monitors in that layout's
  order: left to right by `x`, those at one `x` top to bottom by `y`,
  so `screens.all.first` is the leftmost and a wallpaper per monitor
  goes left to right with `for s in screens.all` (decisions.md
  screen-position).
- **`panel Name { … }`** is a layer-shell surface for launchers,
  notification stacks and dashboards. **`osd Name { … }`** defaults to
  the focused monitor, the overlay layer, and click-through (an empty
  input region). Both honour `screens: focused`, `layer`, `anchor` and
  `keyboard`. A `panel` or `osd` whose `screens:` is written and is not
  `focused` (`all`, a monitor's name, a list, an expression) is on each
  monitor it picks as a bar is: an instance per monitor with `screen`
  in scope and its own state, parked with its monitor
  (`panel Dock { screens: all; width: screen.width / 2 }`). On the
  focused monitor (the default) it is one surface the compositor
  places, and `screen` is not in scope there: reading it is a load
  error saying to add `screens: all`. A `screens:` expression that
  evaluates to `focused` keeps one instance that the compositor places
  on the focused monitor, its `screen` that monitor, changing in place
  as focus moves (as a lock's with `screens: focused` does: nothing is
  mounted again).
  (decisions.md flex, 2026-10-24)
- **`open:`** says whether a surface is shown. Bound two-way
  (`open: <-> open`), Escape, a click away and focus loss write `false`
  (on a `window`, only the compositor's close and `w.close()`, below).
  A click on the surface's own buffer where it takes no input (beside a
  panel's box on the output it is stretched across) is a click away.
- **A closed surface's handlers wait.** While a `bar`, `panel`, `osd`
  or `window` is closed, only its own events run (`on show`, `on hide`,
  `on key`, and the other events of the surface itself). Its
  `on change`, service and timer handlers, and those of its elements,
  do not run, and its timers pause. When it opens, what they missed
  runs once. An `on change` runs if what it watches differs from what
  it last saw while the surface was open, and also for a change made
  in the tick that opens it, compared with the value at the end of the
  tick before, even one that puts back what it last saw. So a handler
  that sets `view` and `open` together is seen by the panel's
  `on change view`. A service event that comes while the surface is
  closed, once its body has mounted, is delivered when it opens (the
  latest 256 per handler). In a surface that starts closed, the
  `on change` handlers written in its body exist from the start, so
  the tick that first opens it is seen too. Before then they have seen
  nothing open, so a change made earlier does not run them, and they
  read what they watch from the start: watching a value from an action
  with a result (`let r = calc(q)`) runs the action while the surface
  is closed. Its elements and components, and their handlers, mount
  the first time it opens, so an `on change` in one of them takes the
  value it mounts with as its first (section 8.4) and does not see the
  tick that first opens it; written in the surface's body, it does.
  A surface's handlers that mount together run in the order written,
  whether it starts open or closed; a handler in an `if` or `match`
  branch, a `for` row or a `popup` that mounts later may run after one
  written below it.
  A `popup` and the `lock` mount their content each time they open
  (the lock's `enter` poses play at every lock; decisions.md
  lock-polish), and the `lock`'s handlers run as below.
  (decisions.md panel-change-closed)
- **`popup { … }`** is an element, not a top-level surface: it is
  anchored to its parent element, shows while its `open` is true, nests
  (a popup may hold popups), and has `on dismiss` (Escape or a click
  away closed it). `trigger: hover` lets the pointer open and close it
  (section 6.3). A popup takes the keyboard (an `xdg_popup` grab) only
  when a press opened it, while that press is still the seat's last
  and at most 500 ms old: a handler or two-way write running for a
  click or a key set its `open`, or a service answered an action such
  a handler ran (a tray menu's `opened`). One a hover, a timer or IPC
  opens does not, nor does a `trigger: hover` popup or one opened from
  inside a popup without a grab, nor one on another monitor than the
  surface the press landed on (a bar's instance there reacting to what
  the press changed).
- **A popup opens away from a `bar`'s edge**, across the bar, below
  its anchor otherwise, and beside its row for a popup in a popup.
  Its `margin` on the side that faces its anchor is the gap between
  them: 6 px unless it is set, `0` touching, negative overlapping the
  anchor (`margin: -30, 0, 0` on a popup of a 30 px top bar covers the
  bar). Its other sides are not used. Along its anchor it is centred
  on the element it is anchored to; a popup in a popup lies level with
  its row's top instead, on the side its `anchor:` names (`left`,
  `top_left` or `bottom_left` to the left of its popup, `top` above,
  `bottom` below, to the right otherwise). Where that place does not
  fit on the monitor the compositor may slide or flip it.
- **`anchor: pointer`** opens a popup where the press that opened it
  went down (any button, on its element, on the surface it nests in),
  down and to the right of that point and touching it unless its
  `margin` says otherwise: a context menu at the click, on a bar too
  (not across the bar). Only the press that opened it counts: a popup
  opened with no press on its element in that input step (a key, a
  timer, IPC, a hover) opens at its element as usual, however recent
  an earlier press was. It keeps its place while it stays open; a
  later press on its element (outside the popup) that leaves it open
  moves it there once logic has answered that press, so a right-click
  on another row opens the menu at that row. (decisions.md flex,
  2026-10-24)
- **A bar reserves its edge**: its thickness and its margin on that
  edge, as layer-shell's exclusive zone. **`exclusive:`** on a `bar` or
  `panel` says how much: `true` its thickness across the edge (a bar's
  default), a length (in px) that much whatever its size, counted from
  its margin as its thickness is (`exclusive: 20` under a 36-tall bar
  with an 8 px margin keeps 28), `false` or `0` nothing, so windows
  go under it (a panel's default). A panel keeps space along the edge
  its anchors make one edge of: its `attach:` edge, or the one edge its
  `anchor:` names (`top`, `left`, …); anchored at a corner or the
  centre it keeps none, layer-shell reserving along one edge only, and
  `exclusive:` there is a warning, as is a length in another unit than
  px. (decisions.md flex, 2026-10-24) The compositor arranges the
  surfaces that reserve one first, from the overlay layer down and in
  the order they were made, each in what the zones before it leave;
  every `bar`, `panel` and `osd` then lies its margin inside what is
  left, from each edge it is anchored to (a bar its edge and both ends,
  a `panel` or `osd` the edges its `anchor:` names, and a panel's
  `attach:` edge).
- **`attach: <edge>`** (a `popup` or `panel`) grows the surface out of
  that edge with concave fillets: its painted box's corners on that side
  are square, with a fillet of their radius beside each. The fillets
  lie outside that box, and a clip above it (a `clip: true` box holding
  the card, a `scroll`) lets the box's fill through there and at the
  square corners they meet, a rounded clip too, at each of the box's
  corners on that side that lies on or inside the clip's box, and only
  as far from the edge as the clip's box reaches (a card overflowing a
  short or narrow clip, or slid out of it, shows no corners past it);
  nothing else passes (what the clip holds before or after the box,
  under it or in it stays inside the clip's box). A popup's
  `attach:` names its own side that touches its anchor (`top` opens
  below it, whatever the bar's edge); a panel's anchors it to that
  screen edge. `attach:` does not move the box: the margin on that side
  is kept like any margin, 0 while unset (a popup's default gap is 0
  rather than 6), so the box touches its anchor, the screen's edge or a
  bar's exclusive zone, and a negative one overlaps it: `attach: top;
  margin: -30, 0, 0` on a popup of a 30 px top bar, or on a panel under
  it, covers the bar and grows out of the screen's edge.
- **`keyboard: none | on_demand | exclusive`** sets how the surface
  takes keyboard focus. While a surface of the shell has it, the
  `keyboard` service's `alt`, `ctrl`, `shift` and `logo` say which
  modifiers are held (false otherwise: no compositor tells another
  client), so a window switcher opened with Alt+Tab commits on
  `on change keyboard.alt` turning false (decisions.md services-round).
- Each layer surface gets a stable layer-shell namespace,
  `strand-<Name>`; a `window`'s `app_id` defaults to the same string.
- **`window Name { … }`** is an app's window, an `xdg_toplevel` the
  compositor manages: it tiles, floats, moves, minimises and is listed
  as any app's window is (a settings window, a picker). (decisions.md
  window, 2026-10-25)
  - It is one surface whatever the monitors (the compositor picks one),
    so `screen` is not in scope in it. `screens:`, `layer:`, `anchor:`,
    `margin:`, `attach:`, `scrim:` and `keyboard:` on it, or in a
    `when` on it, are load errors (`check::window_prop`): the
    compositor places, stacks and focuses a window, and gives it the
    keyboard while it is focused.
  - `title:` is the title the compositor shows (its name while unset);
    `app_id:` is the app id window rules match (`strand-<Name>`, its
    namespace, while unset). Either changes the open window in place.
  - The compositor decides its size. `width:` and `height:` (its
    content's size while unset, springing as content grows as a panel
    does) are the size it asks for; `min_width:`, `min_height:`,
    `max_width:` and `max_height:` are the sizes it accepts
    (`set_min_size`, `set_max_size`). A minimum over the maximum,
    both written as numbers, is a load error (`check::window_min_max`:
    the compositor would end Strand's whole connection on it); one a
    binding makes at run time raises the maximum to the minimum, with
    a warning in the log. A configure that gives a size on an axis
    lays the window out at that size, with no growth spring and no
    other size asked for, when the window is maximised, fullscreen,
    tiled or being resized, or the size is not the one it asked for
    nor one of its own it committed since the compositor's last
    configure (an echo of a configure sent before the compositor saw
    its latest commit, as on a focus change); a configure that leaves
    the size to it (0) keeps its own. A floating window keeps its
    top-left as it grows.
  - **`decorations: server | none`**: `server` (the default) asks for
    the compositor's title bar and borders through `xdg-decoration`,
    `none` asks it to draw none. A compositor may decide otherwise
    either way (sway decorates a tiled window and leaves a fixed-size
    one to its client): **`w.decorated`** (`id: w` on the window) says
    whether it draws them, so a config draws its own title bar where
    it does not, `if !w.decorated { TitleBar }`.
  - **`w.focused`** is true while the compositor has it focused (its
    `activated` state), whichever element in it has the keyboard's
    focus (a button, a popup of it); **`w.maximized`**,
    **`w.fullscreen`** and **`w.tiled`** follow the compositor too.
    `configure_bounds` (the largest size that fits) bounds its
    content's size, and stays its bound when the window enters an
    output; without it, the whole output is.
  - **`w.move()`** and **`w.resize(edge)`** start an interactive move
    or resize from the seat's press, so they are called while the
    press is held (`on change bar.pressed { if bar.pressed { w.move()
    } }`; `edge` an `Anchor`, `top_left` … `bottom_right`; `center`
    does nothing); `w.minimize()`, `w.maximize()`, `w.fullscreen()`
    and `w.close()` ask the rest, with the names and toggles of the
    `windows` service's window actions (`win.maximize()`). An ask the
    compositor does not offer (its `wm_capabilities`) does nothing. A
    maximize, fullscreen or minimize asked in the handler that opens
    the window (`shown = true; w.maximize()`) is asked when the window
    is made, before its first frame; a move, resize or close of a
    window not shown does nothing. On another element they do
    nothing.
  - The compositor's close, and `w.close()`, write a two-way `open:`
    false; a window whose `open` is not two-way stays open, and
    `strand check` warns on one whose `open:` is one-way or unset
    (`check::window_open`; a two-way `open` in a `when` on it is
    enough). Escape and focus loss leave a window open.
  - A popup in a window opens from it as from a panel, `anchor:
    pointer` included; since a compositor never tells a client where
    its window is, neither the window nor a popup in it has a place on
    the screen, so its `id.box` is unset and no shared morph reaches
    it from another surface. Several windows may be open at once; a
    window already open opening again is the same window, and stays
    the same window when its output is unplugged (the compositor moves
    it); a reload keeps an open window open with its states (section
    10.1).
- **`inhibit_idle: bool`**, on any surface, keeps the compositor from
  going idle (no screensaver, dimming or lock by timeout) while the
  surface is shown and the value is true: `bar Top { inhibit_idle:
  caffeine }`. The other side is the `idle` service: `idle.after(t)` is
  true once the seat has had no input for `t`, and an inhibitor holds
  it back too (decisions.md services-round).
- **`lock { … }`** is the lock screen, on `ext-session-lock`. A config
  has at most one `lock`, across its files. It is on every monitor its
  `screens:` picks (all of them by default), a monitor plugged in while
  locked included, and each monitor's instance has `screen` (that
  monitor) in scope, as a bar's has. Unlike a bar's, the lock's own
  `state`s are one for every instance: there is one password, typed
  into whichever monitor's lock the compositor gives the keys, and the
  keys or the pointer moving to another monitor carry on the same
  text. A lock `state` (in its body or its elements) therefore cannot
  start from `screen` or from any `let` of the lock (a load error); its
  `let`s, its elements' own state and the `state`s of its `if`/`match`
  branches, components and `for` bodies are each instance's. Its timers
  and its `on change` and service handlers, in its body and its
  elements, run once for the lock as its `state`s are one (a counter
  steps once, not once per monitor), from the first instance shown,
  paused while none is; they cannot read `screen`, a `let` or an
  element of the lock (a load error). An element's own handlers
  (`on key`, `on activate`) run on that monitor's instance. Every monitor not picked
  shows a solid in the lock's colour (its `bg`). `screens: focused`, or
  a pick that names no plugged monitor, keeps one instance on the
  focused monitor (else the first of `screens.all`, the leftmost: the
  monitor it shows on is the one its `screen` is; decisions.md
  screen-position), whose `screen` changes in place
  when focus moves the content to another (nothing is mounted again, so
  what was typed stays; decisions.md flex, 2026-10-24, and lockmon,
  2026-10-25). A `thumbnail screen` in a lock shows a still of that
  monitor taken just before the lock covered it (the lock request waits
  up to 500 ms for it, at most 1280×720, let go when the lock ends; only
  monitors the lock's thumbnails show are taken); a monitor plugged in
  while locked (a replug of one, or another monitor on its port,
  included: a still goes with the monitor it was taken of) has none, and
  its thumbnail draws nothing, so the lock's own `bg` shows where it
  is, and reads `blank` (section 6.3; decisions.md oi-lock, 2026-10-26).
  Keys typed carry on in the field they were typed into when the
  compositor moves the keyboard to another monitor's lock, focused there
  as on the first (by `focus: true`, a click or Tab). A `lock` in which nothing
  calls `auth.submit` is a load error (it has no way out); a `popup` in
  a lock is a warning, since popups never open on a lock surface. The
  lock is exempt from reload (section 10.1) and **fails closed**: if
  anything in it faults, a built-in password field is shown, on every
  monitor that showed the lock; a fault inside one monitor's instance
  alone (its runtime fault, which freezes that instance only, or its
  first frame missing while another monitor's drew) shows the solid on
  that monitor while the others carry on, and the field once none is
  left.
  Authentication runs in a separate helper through the PAM service
  `strand`, or `login` with a one-time warning when `/etc/pam.d/strand`
  is missing. While a lock is shown PAM's conversation runs: the `auth`
  service's `message` and `prompt` hold PAM's latest text and the hidden
  prompt it waits on, as PAM says them, so a module that needs no
  password (a fingerprint reader) can unlock, and `auth.submit` answers
  the prompt PAM waits on, or the next one it asks. The lock has the
  keyboard, so `keyboard.caps_lock`, `keyboard.num_lock` and
  `keyboard.layout` are its keyboard's own, exact as keys are pressed:
  `if keyboard.caps_lock { text "Caps Lock is on" }`.
- **An admin password dialog and a login screen are ordinary
  surfaces** (decisions.md services-round): no surface kind of their
  own. A panel shown while the `polkit` service has a request,
  `panel Polkit { open: polkit.request != null; keyboard: exclusive … }`,
  is the session's polkit agent while a config reads `polkit`;
  `polkit.respond(pw)` answers it through polkit's own helper. A config
  greetd runs as its greeter logs a user in with `greetd.login`,
  `greetd.submit` and `greetd.start(command)`, each of the command's
  texts one word, and `strand run` ends once greetd takes the session.
  Neither service's answers are recorded, reported or taken by
  `strand call` (section 13), as with `auth`. A Bluetooth pairing
  dialog is an ordinary panel too (decisions.md bt-agent),
  `panel Pair { open: bluetooth.request != null … }`: while a config
  reads `bluetooth.request`, Strand is the session's default BlueZ
  pairing agent, and the request is answered by its own `respond`,
  `accept` and `reject`. `bluetooth` is not a secret service: a typed
  answer, like every action's argument, is never recorded.
- **A password's way out is warned** (`check::secret_flow`, a warning;
  decisions.md oi-lock, 2026-10-26). What an `input` whose `type` may
  be `password` writes (`text: <-> pw`) is a password (`password`
  written on it or in one of its `when` blocks, or a `type` read from
  elsewhere, such as a component's parameter), and so is the key an
  `on key(k)`, an `on key_release(k)` or a claim that takes `(k)` (`on key
  "ctrl+s" (k)`) on or around one hears (`k.text`, `k.name`); a claim
  without `(k)` hears nothing. So is any value made from
  it through `let`s, `state`s it is written to, list writes, `for`
  bindings, component and `fn` parameters, the result of a `fn` or of a
  lambda whose body passes it on (a `fn` making dots of it does not),
  and every operation that keeps its characters (`+`, `?:`, `??`,
  `match`, text methods, `join`, `number`). Reaching any of these is
  the warning: a prop of a built-in element (`text pw`, a
  `placeholder`, a canvas's `draw`, a `file`'s `run:` and `text:`,
  which show, draw, run or write it), other than a password input's own
  `text`; a token,
  a pose or keyframes; an argument of a declared `action`
  (the process list shows it) or of an action of a service or record
  (`clipboard.copy`, `n.reply`, a `from dbus` method), other than
  `auth.submit`, `polkit.respond`, `greetd.submit`, an access
  point's `connect_with`, `network.join`'s `password` and a Bluetooth request's `respond`; a write to a service's field or a settings
  field; and a `state` holding it that is `persist` or exported. A
  `bool` made from it (`pw != ""`, `pw.contains(" ")`) and its length
  (`pw.len`) carry nothing: password dots and a field that changes
  colour while typed are fine. Flows are followed over the whole config
  rather than per call, so a component given a password by one call is
  checked as if every call gave it; which branch runs is not followed
  (`if pw == "x" { a = 1 }` makes nothing a password).

### 5.2 Components and slot

- `component Name(params) { tree }` declares a node kind of your own. It
  is called with the one call shape (section 6.1): `Dot ws`,
  `Toast n { dense: true }`, `Clock`.
- Parameters are `name: Type = default`. A call passes them by position
  (the positional fills the first parameter) or by name in the call's
  block, as props. A parameter with a default may be left out; one
  without a default must be given.
- A parameter's type may be left out where it can be inferred from its
  default or from the values its callers pass; where it cannot, it is a
  load error asking for the type.
- Parameters are read-only inside the component; assigning to one is a
  load error.
- A component whose tree is one element (beside its `state`, `let` and
  handlers; no `if`, `for`, `match` or `slot` at its top) stands for
  that element: handlers and `id:` written in a call's block are the
  root element's (`Chip "a" { id: c; on click { n += 1 } }`, then
  `c.hover`). The handlers run in the caller's scope and are checked
  against the root element's events; a call whose root is another
  component's call reaches the element at the bottom. On a call of a
  component whose tree is not one element, either is a load error
  naming the fix (wrap the call in a `box`). A component with an `id`
  parameter takes `id:` as its argument.
- `screen` in a component is the screen of the surface instance it is
  mounted in, as in that surface itself (section 5.1): a `bar`'s, a
  `panel`'s or `osd`'s whose `screens:` picks monitors, or the
  `lock`'s; read-only, and on each monitor's instance that monitor. A
  component that reads it, or calls one that does, gets it from each
  call, which passes the `screen` in scope there; a call where there is
  none (in a `panel` or `osd` on the focused monitor, or a `popup`
  inside one) is a load error at the call. A parameter, local,
  top-level declaration, enum variant or service named `screen` is the
  one read instead: the component's `screen` is found only where the
  name would otherwise be unknown.
- Children written in a call's block render where the component's tree
  has `slot`. Children passed to a component without a `slot` are a load
  error, and so is `slot` outside a component. Each copy of a slotted
  subtree has its own state.
- `component Name(params) tokens { … } { tree }` exposes component
  tokens (section 9.1), read inside as `$Name.token`. (M6) When another
  file declares a component of the same name, `$Name.token` still means
  the file's own (section 4.2); another file names it `$file.Name.token`
  where a bare path would be ambiguous.
- Components hold state (section 5.3). A cycle of components that always
  mount each other is a load error naming the path.

### 5.3 state, let and export

- **`state x = expr`** declares a writable cell. Its initial value is
  the default expression, evaluated once when the cell is created.
  `state x: T = expr` gives the type; `state xs: [T] key f = []`
  declares a keyed collection (section 6.5), and `state m: [K: V] =
  []` a dictionary (section 7.1), which is keyed by its keys: a `key`
  clause on one is a load error (`check::dict_keyed`).
- **`let x = expr`** declares a derived, read-only value. It is
  recomputed lazily when what it reads changes. Assigning to a `let` is
  a load error.
- **Where state lives.** `state` may be declared in four places: at
  the top level of a file (one cell for the program); directly in a
  component's body (one cell per instance); directly in a surface's
  block (one cell per instance of the surface); and directly in a `for`
  body or in the block of the element written directly in it (one cell
  per item, per instance of the enclosing component or surface).
  Anywhere else it is a load error, including any element nested in a
  component or surface: `component Card { col { state open = false } }`
  and `text "a" { state s = 0 }` are rejected, and the fix is to move
  the `state` up to the component, surface or `for` body it belongs to.
- **Where let lives.** `let` may be declared at the top level of a
  file, anywhere in a component's or surface's tree (not in a
  props-only block such as a `when`), and in a handler or `fn` body as
  a local binding.
- An untyped `state i = 0` is an `int` until a fraction is written to
  it; then it is a `float`. The same holds for a list literal of whole
  numbers (`[1, 2]` is an `[int]`, and a `let` or a handler's local
  holding one is never written, so it stays one) and through `?:` and
  `match` whose branches all have that shape, an empty list fitting any
  list (`match name { "DP-8" => [1, 2], _ => [] }` is an `[int]`). A
  `for` over such a literal loops over `int`s (`for w in [1, 2, 3] key
  w` gives each `w` as an `int`). An untyped `state` whose first value
  is whole by any of these (`state size = w`, `state cur = sizes[0]`, a
  component's inferred parameter) is a `float` once a fraction is
  written to it, as is the value it came from, and a fraction pushed or
  inserted into a whole list makes it a `[float]`.
- **`persist`** (`state x = 0 persist`) keeps the value across restarts
  (section 10.3). It is allowed only on a `state` holding plain data
  (lists, dictionaries and records of it): not functions, `Async`
  values, runtime handles or live service items.
- **`export`** (`export state`, `export let`) makes a top-level value
  readable from other files and from the command line as `file.name`
  (section 4.2). It changes nothing else.

### 5.4 Enums and record types

- `enum Kind { volume, brightness }` declares a closed set of variants.
  A variant is written by its bare name wherever the expected type is
  known (`state kind = volume`, `kind == volume`).
- `type Pin { app: AppId; label: text }` declares a record. Records are
  built with call syntax and named arguments: `Pin(app: a, label: "x")`.
  An optional field may be left out (it is null), and so may a list
  or dictionary field (it is empty), so a record that gains one,
  builtin or your own, stays buildable as before; every other field is
  needed. Fields
  are read with `.`.

### 5.5 Functions

- `fn name(params) -> Type { body }` declares a function. The value of
  the body is its last statement, which must be an expression.
- `fn`s are **pure**: an assignment or an action call in a `fn` body is
  a load error, and so is `await` (section 7.2). A `fn` may call itself;
  runaway recursion is a runtime error value, never a crash.

### 5.6 Custom services and permits

- `service name from dbus system|session "bus.Name" ["/object/path"]
  { fields }` declares a service backed by a D-Bus object. Its fields
  are checked against the object's introspection. A field written
  `name: type rw = Property` is writable (section 8.1); without `rw` it
  is read-only. (dbus-unfollowed) A field bound to a property that its
  introspection annotates as never signalling its changes
  (`org.freedesktop.DBus.Property.EmitsChangedSignal` `false`, on the
  property or its interface) is a warning, `check::dbus_unfollowed`: the
  field would keep the value it read at start; `const` and
  `invalidates` are followed.
- `from file path { fields }` reads a file, again whenever it changes
  (a file a change leaves empty is read again 50 ms later, since a
  rewrite in place truncates before it writes); `from listen command`
  reads the lines a command prints; `from poll command every T` runs a
  command, or reads a file, at an interval. Their fields are checked
  against the schema you declare.
- `from dir path { files: [File] }` (services-round) lists a
  directory's files: its document is `{ files: [...] }`, each a `File`
  (`path`, `name`, `modified: Date`, `size` in bytes) for a regular
  file or a link to one, hidden files (a name starting with `.`) and
  subdirectories left out, ordered by name, the first 10 000 by name
  (a warning says how many more there are). It is listed again
  whenever an entry is added, removed, renamed or rewritten (changes
  within 50 ms listed once, and a directory that keeps changing at
  most every 500 ms), never on a clock. A directory that does not exist yet reads as no
  document (every field its default) until it is made. `File` and
  `Date` are the builtin records a service's fields may hold besides
  your own `type`s.
- (doc-formats) A `Date` filled from a document (a field, a field of a
  declared `type` at any depth, a list item, a listen line, `-> Date`)
  reads a record of its fields or date text, trimmed, the first form
  that parses winning: digit text by its count of integer digits, 8
  as `YYYYMMDD`, 12 as `YYYYMMDDHHMM` and 14 as `YYYYMMDDHHMMSS` (the
  wall time as written), 9 to 11 as Unix seconds, 13 as milliseconds,
  16 as microseconds and 19 as nanoseconds, any other count no date;
  RFC 3339 / ISO 8601 with a zone (also without seconds, with `+hhmm`
  or `+hh`, or `20261107T195510Z`); RFC 2822, a leading weekday
  ignored when it is wrong or written in full; a naive `YYYY-MM-DD[T
  ]HH:MM[:SS]` or `YYYYMMDDTHHMM[SS]`, the wall time as written;
  `YYYY-MM-DD`, hour and minute null. A trailing ` UTC` reads as `Z`. A number reads as its digits written out do, so `20261107`
  printed alone (which a document reads as a JSON number) is 7
  November 2026, and `2026` or `0` is no date. An instant is
  moved to the local zone and cut to the minute; one whose wall time
  falls outside the dates Strand holds is no date. Other text does not
  convert: the default and one report, or null for `Date?`. A `Date`'s
  default is 1970-01-01 with no time of day, and a `Date` without a
  time of day formats as its midnight (`%H:%M` is `00:00`).
  `strand set` and `strand call` read date text the same way. A
  `key=value` line's key starts with no digit, so a date or a time
  printed alone is text, not a pair.
- (doc-formats) **Documents.** A file, a poll's output, a listen line
  and an action's output are each one document: JSON when it parses as
  JSON; else XML when, a UTF-8 BOM removed and trimmed, it starts with
  `<` and parses as XML; else `key=value` (or `key: value`) lines when
  every line is one (blank and `#` lines aside); else text. Text
  starting with `<` that is not XML (an HTML page) is text, never pairs,
  and the service logs why once, until a document is something else. XML nested deeper than 128 elements,
  with more than 64 attributes on an element, or with a DTD declaring a
  parameter entity, an external entity or an entity whose value holds
  `&`, `%` or `<`, or whose entities expand past the document's size
  cap, is not read as XML; a DTD is otherwise allowed, and nothing
  outside the document is ever fetched.
- A document is at most 4 MiB: a file larger is not read (cut short it
  would not be the document) and its fields keep their last values,
  logged once per size; a command printing more is ended and its
  output ignored; a longer listen line is skipped. Bytes that are not
  UTF-8 are read as windows-1252 when an XML declaration at the start
  names ISO-8859-1, Latin-1, windows-1252 or US-ASCII (as browsers
  do), and otherwise with U+FFFD in place of what is not UTF-8.
- An XML document's root element is the document (its name is not a
  key segment). An element with neither attributes nor child elements
  is its text (CDATA and entities decoded, ends trimmed, inner line
  breaks kept); any other is a record of its attributes (`@name`), then
  its child elements and non-blank text runs (`#text`) in document
  order. Names keep the prefix the document writes (`dc:creator`).
- A name `n` in a key path or a declared type's field finds, in order,
  the first of: child elements named exactly `n`; the attribute `@n`;
  child elements `p:n` with any prefix; attributes `@p:n`; and, for
  `text`, the element's own text. A key path's first segment is searched
  for depth first when the root lacks it (`= item` finds RSS's and
  RSS 1.0's items alike), and the first element found holding it gives
  its matches (a GPX track's points across two `<trkseg>`s are read as
  `[Seg]`, each with its `trkpt`s); each later one is read in the first match of
  the one before (a number picks that match); the last segment's
  matches are the value, several of them a list. A string key (`=
  "dc:creator"`, `= "@state"`, `= "#text"`) is one exact segment.
- The declared type decides, for every document: a list type over one
  value is a list of it if it converts (else it does not convert),
  text of several values inside a document (several lines, or a
  further word that is itself a number, in a JSON string, an
  element's text or a `from listen` line) only as a list of `text` or
  `path` or of a record that reads text (`<ports>22 80 443</ports>`
  read as `[int]` does not convert, where a number with a unit would
  read the first alone; `45 °C` is still one item), a
  record (a JSON object, an element) only when it holds one of the item
  type's fields, so an API's error object read whole as `[T]` (an
  action's `-> [T]`, or a key that finds the object) is reported
  rather than one item of defaults; a missing key `[]`, with no report; blank text (an
  empty element, a command that printed nothing) read as a list is
  `[]`, a list of `text` too, and
  read as a record type other than `Date` its fields' defaults; a single type over a list reads its first item; an
  XML element read as text, a number, a bool, an enum, a path or a
  `Date` is its text (its own and its descendants' in document order;
  where it has child elements, whitespace collapsed and the runs,
  trimmed, joined by a space except before closing and after opening
  punctuation, so `H<sub>2</sub>O` reads `H 2 O`), and one with no
  text does not convert; a JSON object is never text; a record type
  with a field named `text` reads text (an element of text alone,
  `<guid>x</guid>` beside `<guid isPermaLink="false">x</guid>`) as
  that field, its other fields absent, unless that field's type is
  a record (`type Node { text: Node? }`), which does not read text; `length`,
  `angle` and `duration` read plain number text as a number (px, deg,
  seconds); a record's fields are found by the lookup above, a list
  field taking every match; blank text read as an optional type other
  than `text` is null. A value inside a field's (a list's item, a
  record's field) that held something and does not convert is reported
  once with its path (`` `news.posts`: `item[0].pubDate` holds … ``),
  the item left out or the field its default; the whole field failing
  later replaces that report.
- (lines-list; decisions.md lines-list) **A list of lines.** A whole
  document that is text (a polled command's output or file, a `from
  file`, an action's output), or `key=value` lines holding none of the
  service's fields' keys, read as a list (a field typed `[T]` or
  `[T]?` with no key path, an action's `-> [T]`) is its lines, an item
  each: a line is what section 5.8 frames (`\n` or `\r\n` ends it, a
  bare `\r` redraws it; a file's lines too), trimmed, and a blank line
  is no item, so a trailing newline adds none and nothing printed is
  still `[]` (null for `[T]?`). Each line converts as one value: `text`
  and `path` are the line, a JSON string's quotes removed (`jq
  '.[].name'` prints `"a"`); a number, length, angle, duration, `bool`,
  colour, enum or `Date` is the line read by the rules here (`45 °C`
  on each line is 45 each). A record is the line read as a `from
  listen` line is (JSON lines from `jq -c` or `journalctl -o json` a
  record each, a line naming none of its fields read as written by its
  `text` fields), and a line that fills none of its fields is no item;
  but a list of records splits only where some line names one of its
  fields (a JSON object, `key=value` pairs or XML holding it) or the
  record has a field named `text`. Otherwise the document is read whole
  as before, so plain text (a 429 page's `Too Many Requests`, `pacman
  -Q`'s `name version`) read as `[Post]` is reported, `key=value` lines
  naming the record's fields are one record, and text starting with `<`
  that is not XML (an HTML page) is never a record a line. A line that
  does not convert is left out and reported once with its index (``
  `pkgs.names`: `names[2]` holds … ``), as an item inside a document
  is, and for an action as a warning in the log, once until a call's
  result reads whole; an action's output of lines none of which
  converts is no list, the call's `.error`. Spaces, tabs and commas
  separate nothing (`\0`, a control character, is dropped): a line of
  several values, `pidof`'s `1234 5678`, is no item of a list of
  numbers, and its report says to print them one per line or read the
  text whole (`-> text`, a `text` field) and its values with
  `numbers(…)`. JSON and XML keep their reading, so a pretty-printed
  array spanning lines is one array and XML's root one item, and so
  does a single type over several lines: `text` is the whole, a number
  the first (`/proc/loadavg` read as a `float`). A `from listen` line
  is one document, read as a list one item.
- A field typed `text` reads an XML fragment as written, markup and
  all, when the document is one element of text alone (`<b>CPU</b>`)
  or, for `text` but not `text?`, when it holds nothing at the key of
  any of the service's fields (an HTML fragment in a file, `<span
  foreground="red">92%</span>` printed by a script; the root's own text
  read by a field named `text` holds nothing): markup a source
  prints stays markup for `markup:` (section 6.2), as it does in a text
  document. A document that holds some field's key is data, so a
  `text` field whose key it lacks is absent there (`""` for a file or a
  poll, and a `from listen` line leaves the field as it was); a
  document with anything before its root element (an XML declaration,
  a DOCTYPE, a comment) is data and never read as written. `text?`
  reads null for a key the document lacks, as with JSON; other types
  read the element tree; an action's `-> text` is what it printed.
- (proc-format; decisions.md proc-format) The same holds for every
  structured document: a field typed `text` (not `text?`) reads a JSON
  object, `key=value` (or `key: value`) lines or an XML fragment as
  written when it holds nothing at the key of any of the source's
  fields, every other field absent there as above. The source's fields
  are a service's, an action block's (section 5.7) or a `-> T`
  record's; for a `from listen` line or an action's line the document
  is the line. So `{ line: text }` reads pacman.log's
  `[2026-11-08T16:04:17-0700] [ALPM] transaction completed`, `error:
  failed to commit transaction` or `http://example.com/x` as printed,
  where the first `:` or `=` would make it a pair whose key no field
  names; a document holding some field's key is data (`error: x` read
  by `{ error: text?; line: text }` fills `error`, and `line` is absent
  there), so a line is read as pairs only when the config names its
  key. A field typed `text` or `text?` reads a JSON number, bool or
  array as written (`1.10` stays `1.10`, `[1, 2]` is `[1, 2]`), a JSON
  string as its value, and JSON `null` as nothing (`""` for `text`).
  A command's output (a polled command's, a `from listen` line, an
  action's) is framed as a terminal shows it before it is read
  (section 5.8).
- A `from listen` service has one event, `line(doc)`: each line the
  command prints, `doc` holding that line's fields alone (the service's
  own record: a field the line leaves out is null when its type is
  optional, its type's default otherwise, and a required `text` field
  holds the line as written when the line holds no field at all). Lines printed faster than a
  frame are merged into the fields but each is still one `line` event,
  queued as `notifications.received` is, so `on player.line(doc)` sees
  every line. A line handler reads the service: the command runs while
  the handler is mounted, and lines printed before it was are not
  heard. (proc-lines) A command's `line` events are external input
  (section 8.7), so a handler that appends every line is never
  throttled; they are still a service's events, not gestures, so a
  line that comes while the handler's surface is closed is delivered
  when it opens, as any service event is: a closed surface catches up
  on the latest 256 per handler, the older ones dropped. While a
  handler hears them none is lost, and their queue is bounded: while
  more than 4096 lines (or 4 MiB) wait for handlers, strand stops
  reading the command's stdout until they are heard, so a fast command
  waits as it would on a slow terminal; its stderr has a pipe of its own and is
  still read. The fields and `line` read stdout alone (section 5.8).
  The command's stderr is kept: why it failed (section 5.8) is in the
  service's diagnostic when it fails or ends.
- A polled command runs at most every 100 ms: an `every` shorter than
  that is a warning, and the command runs every 100 ms instead. A
  polled file has no floor and is read every `T`. (proc-ok) A polled
  command may list after its interval the exit statuses that are no
  failure, `ok 0, N…`, as an action's command may (section 5.7): `from
  poll ["pacman", "-Qdtq"] every 1h ok 0, 1 { names: [text] }`.
- Running a command (`listen`, or `poll` of a command) needs
  `permit exec`, at the top level or in the service's block, optionally
  listing the programs allowed; without it the service is a load error.
  A `poll` whose argument is a string naming a path with no whitespace
  (`/…`, `~/…`, `./…`) reads that file each interval and needs no
  permit; to run a program by its path, give the command as a list
  (`["/usr/local/bin/gpu-temp"]`) and permit it. A polled or `from file`
  path that is a program is a warning at check time and a runtime
  failure, never parsed as a document.
- A custom service starts when the program first reads it and stops
  5 s after its last reader leaves, as builtin services do (section
  8.1). Changing its declaration restarts only that service.
- (service-ready) Every service, builtin or declared, has a read-only
  `ready: bool`: a run of it is up and has answered. A `from file` or
  `from dir` service is ready once its first read is in, a `from poll`
  one after its first poll that answers (a command that fails, times out
  or prints more than a document leaves it not ready, though the first
  frame does not wait for it, and later keeps its last values), a
  `from listen` one once its command runs,
  and a `from dbus` one once its properties are read and while the
  daemon owns its name (false while it is gone, true again once a new
  one has been read). The name is reserved: a declared field or action
  named `ready` is a load error (`check::reserved_field`), and a
  service schema declaring one is refused. Section 8.4 says when it
  changes. A builtin the shell fills itself, with no run (`screens`,
  whose monitors main reports, `clock`, `calendar`), is ready from the
  start, so a `file` reading only it never waits and `on change
  screens.ready` never runs.
- **Plugin services.** A service may also come from a plugin: a binary
  built from `strand`'s library with services of its own (git-only and
  marked unstable). Its schema is a
  `.schema` file in `$XDG_DATA_HOME/strand/schemas/` (written by the
  plugin binary's `--write-schemas`), which `strand check`, `strand run`
  and the language server all read, so a program that reads a plugin
  service checks the same way everywhere. A file that is not a regular
  UTF-8 file under 1 MiB, does not apply, or declares a builtin service
  is skipped with a warning. A file declares only its own service, the
  one it is named for (`<service>.schema`), and the records, enums and
  aliases it uses; one that declares another service, or an element,
  function, value, method or token, is skipped with a warning naming it
  (decisions.md flex, 2026-10-24). When
  the running binary does not serve a service a file declares, reads
  give its schema defaults and writes, calls and actions are refused,
  with a notice naming the file while the program reads it. A schema
  cannot declare a dictionary `[K: V]` yet (a field, an action's
  parameter, a result): such a file does not apply, its warning saying
  to use a list of a `record`. A value holding a dictionary that would
  reach a service any other way (a write, an action's argument) is the
  action's error "a service cannot take a dictionary yet", never a
  silent null (decisions.md dictionary: D-Bus and JSON maps are phase
  2).

### 5.7 Actions

(M6, the owner's ruling; decisions.md m6-w2-language.)

- `action name(params) [command]` at the top level declares an action
  that runs a command. Every parameter has a type and no default; the
  type is one of `text`, `path`, `int`, `float`, `bool` or an enum, or
  (proc-list) a list of one of these (`[text]`, `[path]` …); a list of
  lists or of records is a load error (`check::type_mismatch`, whose
  help passes `json(v)` instead).
  The command is a list literal whose items are text literals and the
  action's parameters, nothing else; its first item, the program, is a
  text literal. The program must be allowed by `permit exec` (section
  5.6), else it is a load error. A parameter the command never uses is
  a warning.
- A handler calls it as a function: `on click { dispatch(3) }`. The
  call is checked as a function's (arity, argument types) and, as every
  action call is, allowed only in a handler (section 8.3). Each
  parameter becomes exactly one argument of the program, its value as
  `text` shows it, never split on spaces, and (proc-list) a list
  parameter one argument per item, each as `text` shows it (none for
  an empty list, each `[path]` item's `~/` expanded as below): the
  program is run directly, with no shell between strand and it. A `path` parameter whose value
  starts with `~/` reaches the program with the home folder (`$HOME`,
  when it is absolute) in place of that `~`, as every other path strand
  takes does (a settings file, a `from file`, an image); a bare `~`,
  `~user/…` and a `text` parameter are passed as written, a bare `~` and
  `~user/…` as those other places leave them (decisions.md path-tilde).
  What the program does with an argument is its own: a shell's `-c`
  runs the argument after it as a
  script (`["sh", "-c", cmd]` runs `cmd`'s value as shell code; pass a
  value after a written-out script instead, where it is `$1`), and an
  argument starting with `-` may be read as an option (`--` before it,
  where the program takes one). A parameter right after a shell's `-c`
  is a warning (`check::shell_script`), a list parameter too; pass a
  list after a written-out script, where it is `"$@"`: `["sh", "-c",
  "pacman -Qi -- \"$@\"", "sh", pkgs]`. `--` before a list of names
  is the author's to write, where the program takes it (`["pacman",
  "-S", "--", pkgs]`).
- An action without a result (no `-> T`) runs at most once at a time:
  a call while its command still
  runs queues one re-run, the latest call's, started when the command
  ends, as a `file`'s `run` is (section 9.7). (action-coalesced) So
  calls made together are lost but for the first and the latest: a
  call in a `for` body of a handler, or one after a call of the same
  action that runs first on every path of the handler, is a warning
  (`check::action_coalesced`), whose help offers one call for all
  items (a list parameter: `remove(checked.map(p => p.name))`) or a
  `-> text` action awaited each time. A service's own
  actions are each their own request and are not warned about.
- Its command runs detached, in its own process group, with stdin on
  `/dev/null`; (proc-run) strand reads its stdout and stderr (section
  5.8) and holds them open past its own exit (proc-keeper), so the
  command never dies of a closed pipe, nor waits on a full one, when
  strand exits or restarts; the handler does not wait for it, and logic is
  never blocked by it. A program that cannot start or exits with a
  status its `ok` does not list (below) is
  logged and becomes a `strand watch` notice naming the action, saying
  why it failed (section 5.8), as a `file`'s `run` failing does
  (section 9.7). The handler's next
  statement has already run: the call's value is `()`. An action with
  a result (below) differs in each of these.
- (flex; decisions.md flex) `action name(params) -> T [command]`
  declares an action whose command's output is its value: a call is an
  `Async<T>` (section 8.6), not an action. `T` is a type a `from poll`
  field may have: `text` or `path` (what it printed, trimmed), a
  number, length, angle, duration, `bool`, colour or enum (read from
  the printed text), a record `type` the config declares, the builtin
  `File` or `Date` (section 5.6; decisions.md services-round), or a list
  of these, or any of these optional; any other (a live handle such as
  `Window` or `Canvas`, a font) is a load error. A record or list is read from
  JSON or XML (the root element as `T`), a record also from `key=value`
  lines, a list also from text, a line an item (lines-list), as section
  5.6 reads a document; nothing printed is `null` for an optional `T`. An action has no key path, so `-> [T]` over XML
  reads the root as one item, and a feed's entries need a type holding
  them (`type Feed { entry: [Entry] }` and `-> Feed`). The
  parameters, the command and `permit exec` are as above.
  - In a binding (`let r = calc(query)`, `text calc(query) ?? "…"`) the
    call is a load, as `apps.search(q)` is: it runs when first read,
    runs again when an argument changes, and a newer call supersedes
    the one in flight, whose command is ended (its process group gets
    SIGTERM, then SIGKILL half a second later). The value keeps its
    last result while a new one loads (`.pending`) or after one fails
    (`.error`). In a binding's lambda it is a load error (its answer
    could not reach the binding), and in a `fn` too (`fn`s are pure).
  - In a handler, `await calc(q)` waits for it and is `T`, or the
    handler's error. A call written as a statement (`on click {
    calc(q) }`) is a load error (`check::async`), as a dropped `sleep`
    is: its value would be dropped and its command ended at once; an
    action run for its effect alone has no `-> T`. A call whose value
    no one keeps (neither awaited nor stored) is ended at the end of
    that step.
  - Every call runs at once on a thread of its own, never queued behind
    another. Its stdout is read, at most 4 MiB (more ends it, an error),
    and its stderr is kept for why it failed (section 5.8). It has 10 s, as a `from poll` command
    has: one still running then (or still holding its output open, a
    child it left in the background) has its process group ended as a
    superseded one's is, and the value's `.error` is
    ``"`qalc` timed out after 10 s"``. A program that cannot start,
    exits with a status its `ok` does not list, prints too much or
    prints what does not read as `T` is the value's `.error`
    (``"`qalc` failed (exit status: 1): error: …"``, the headline, then
    why, section 5.8) and an info log line, not a `strand watch`
    notice: the config reads `.error`.
- (proc-ok; decisions.md proc-ok) `ok 0, N…` after an action's command
  (and after a polled command's interval, section 5.6), before any
  block, lists the exit statuses that mean the program did its job:
  `action updates() -> [text] ["checkupdates", "--nocolor"] ok 0, 2`,
  checkupdates' 2 meaning "no updates" (it prints nothing, so `[]`;
  otherwise an update a line, a line an item, section 5.6).
  Each is 0 to 255
  (`check::ok_status` otherwise), and 0 must be among them (`ok 2` is a
  load error, `check::ok_without_zero`, whose help writes `ok 0, 2`),
  so the clause reads rightly on its own. A listed status is no
  failure: a `-> T` reads its output as `T` (nothing printed is `""`,
  `[]` or null, by `T`), a poll's fields update, `error` stays null and no notice is
  shown; the run's `code` (below) still holds it, so `backup.code == 3`
  can say "saved; some files unreadable". A value read (a `-> T` call,
  a polled command) whose program ended with a listed status other
  than 0 having printed nothing on stdout but something on stderr fails
  as an unlisted status does, `.error` holding why (decisions.md
  call-code); otherwise what it printed is the answer, and its stderr
  is logged at info. A job keeps its lines, so its listed status is no
  failure whatever it printed. A signal is never ok. Without
  `ok` only 0 is. `ok` is allowed on a command action, with or without
  a result, and on a polled command; on a `from listen` service (its
  command ending always means a restart), on a `from dbus` action and
  on a polled file it is a load error (`check::ok_not_here`). It is
  for a status the program documents as "none" or "partly" (grep's 1,
  diff's 1, rsync's 24, restic's 3, borg's 1). pacman and yay exit 1
  both for `-Qdtq` or `-Qua` finding nothing, printing nothing, and for
  `-Qi nosuch` failing, printing only why on stderr, so `ok 0, 1` on a
  call or poll reads the first as `""` or `[]` and the second as
  `.error`.
- (lockmon; decisions.md lockmon) An action declared with a command
  has a run, read through its name as an `ActionRun`: `rec.running`
  (`bool`) is true while a command of it runs (for an action with a
  result, while any of its calls' commands does; several may run at
  once); `rec.started` (`Date?`) is when the one running longest
  started, to the minute, null while none runs; `rec.stop()` stops
  them. `running` and `started` read as fields do, in a binding too,
  tracked (`on change rec.running` fires as commands start and end);
  they are the runtime's to say and never written (`check::read_only`).
  (action-error; decisions.md action-error) `rec.error` (`text?`) says why
  its last command failed: it could not start, or exited with a status
  its `ok` does not list (section 5.8 says what the text holds). It is
  null to begin with, from the moment the action is called again, and once
  a command ends well or is stopped; so `on change rec.error` hears a failure
  a shell can show. It is never set on an action with a result, whose call
  has its own `.error`.
  `stop()` is an action, a handler's alone (section 8.3): every command
  of the action now running is stopped and a re-run queued behind one
  dropped. Every program strand starts begins with no signal blocked or
  ignored, whatever strand holds for itself (decisions.md child-signals).
  Each one's process group gets SIGINT, as a terminal's Ctrl-C
  sends it, then SIGTERM 2 s later if its program has not ended, then
  SIGKILL 2 s after that; strand's thread that started the command
  sends these and reaps it, never signalling a group whose id was
  handed on. A stopped command is no failure (no `strand watch`
  notice); a stopped call of an action with a result has the `.error`
  ``"`qalc` was stopped"``, which a handler awaiting it gets. A call
  after the `stop()` queues behind the stopped command as any call
  does, so `{ rec.stop(); rec(f) }` restarts it once it has ended. A
  local or parameter of the action's name is that local. A `from dbus`
  service's actions (methods, `ppd.hold`) have a run too, read as
  `ppd.hold.running`, with no `stop()` (below). A reload
  keeps every run: it never stops a command. A glitch report's replay
  (section 13) runs no command: a command counts as running from its
  call to where the recording says it ended, or to its `stop()`, and
  (proc-run) a run's lines, status, reason, block fields and `line`
  events are replayed from the recording.
- (proc-run; decisions.md proc-run) An action with a command and no
  result also has its last run's output, read through its run:
  - `rec.code` (`int?`) is the status its last command ended with,
    `128 + n` for signal n, as a shell's `$?` says it (130 when a
    `stop()`'s SIGINT ends it; a program that catches SIGINT ends with
    a status of its own, `rsync` with 20); null before any ended and
    from the moment it is called again.
  - `rec.lines` (`[Line]`) is what its last command printed, as a
    terminal shows it (section 5.8): the last 1000 lines, at most
    256 KiB, of stdout and stderr in the order strand read them, the
    last possibly the open line. A `Line` is `n`, its number in the
    run from 1 and its key, so `for l in rec.lines` keeps each line's
    node as old lines leave; `text`; `stderr`, it came on stderr, where
    programs write diagnostics and progress alike, never a severity;
    and `open`, no line break yet (a bar being redrawn, a prompt): it
    may still change.

  `lines`, `code`, `error` and the block's fields (below) are reset
  when a run starts, a queued re-run included, never when one ends, so
  after a failure what it printed is still there; strand keeps them
  where it runs the command, so a reload keeps them as it keeps the
  run. When a command ends, one flush carries, in this order: its last
  `line` events and field merge, the last of `lines`, `code`, `error`,
  then `running` turning false, so `on change rec.running` already
  sees every line and why it failed. A stopped run keeps what it
  printed; `code` says how it ended and `error` stays null. An action
  with a result has neither (several of its calls may run at once, so
  one `lines` would mix them): its `lines` is `[]` and its `code` null,
  and reading either is a warning, `check::no_run_output`, whose help
  says "drop the `-> T`, or read the call's `.error`". A `from dbus`
  action's run has neither: reading one is a load error.
- (proc-run) An action without a result may end with a block of
  fields, filled from its stdout lines as a `from listen` service's
  fields are (section 5.6: types, `= key` paths, the conversions, lines
  faster than a frame merged):

  ```strand
  action backup(dirs: [path]) ["restic", "-r", "/mnt/usb/restic", "backup", "--json", "--", dirs] ok 0, 3 {
    message_type: text
    percent_done: float?
  }
  ```

  `backup.percent_done` reads beside `backup.running`. The fields read
  stdout's ended lines alone; stderr never reaches them. `on
  backup.line(doc)` hears every ended, non-blank stdout line, `doc`
  that line's fields alone, while some handler hears them (lines are
  queued only then, bounded as section 5.6 says); a handler never
  starts the command, only a call does. Without a block an action has
  no `line` event (`on rec.line` is `check::unknown_event`, whose help
  declares `{ line: text }`). The block holds fields only. A block on
  an action with a result is a load error, `check::block_with_result`
  (its output is read whole, as `T`). A field named `running`,
  `started`, `error`, `code`, `lines` or `stop` is a load error,
  `check::reserved_field`, whose help gives it a key path (`err: text?
  = error`), as is one named `ready`, which the service serving the
  block answers itself, and an action with a block cannot be named
  after a builtin service (`check::redeclared`; decisions.md
  proc-language).
- `strand check` lists every action's command, each parameter shown as
  `{name}` where it is one argument and (proc-list) a list parameter as
  `{name…}` where its items go (`tx_run: upkeep-tx run {op} {helper}
  -- {pkgs…}`), then its `ok` statuses; the language server shows it,
  and the block's fields, on an action's hover. Both check its program
  against `permit exec`, seeing through `stdbuf` and `env` (section
  5.8).
- In a `from dbus` service's block, `action name(params) = Method`
  declares an action that calls a method of the service's object.
  Parameters are as above, plus `[text]`. The method is checked against
  the object's introspection as fields are (section 5.6): a missing
  method is an error with a did-you-mean, as is another number of
  arguments or a parameter whose type does not convert to the
  argument's D-Bus type. A handler calls it as a service action:
  `on click { ppd.hold("performance", "game", "strand") }`. An enum
  argument is sent as the daemon has spelled it (as a field write is).
  The call does not hold up the service, and its answer is waited for
  however long the daemon takes (a method may wait on polkit's password
  dialog); the daemon's error is logged, as a builtin service's action
  failing is. When the object's methods cannot be read, the actions are
  not checked and a warning says so. Any other source's block declaring
  an action is a load error.
- (dbus-action-run; decisions.md dbus-action-run) Such an action read
  without a call is its run, an `ActionRun` as a declared command
  action's is: `bolt.enroll.running` is true while a call of it waits
  for its answer, `bolt.enroll.started` is when the oldest of those was
  made (to the minute), and `bolt.enroll.error` (`text?`) says why its
  last call failed: the daemon's error name and message
  (``"org.freedesktop.bolt.Error.Exists: device already stored"``), or
  ``"`org.freedesktop.bolt` is not running"`` or ``"`…` has no method
  `EnrollDevice`"`` when the call could not be made, or why the service
  could not take it at all (``"`bolt` is not running: its body failed
  and restarts after a backoff"``, ``"no system bus"``), which is the
  action failing, never the handler's error (section 12). A call still
  waiting when the service's run ends (it stops 5 s after its last
  visible reader goes, or its run failed) has lost its answer: the
  action runs no more, its `error` ``"the service stopped before
  `org.freedesktop.bolt` answered; whether the call took is unknown"``.
  `error` is null to
  begin with, from the moment the service takes a new call, and once one
  is answered without an error; so `on change bolt.enroll.error` hears a
  failure a shell can show (unless the new call fails before the logic
  thread's next flush, as a command action's may). They are tracked,
  read in a binding or a handler, and never written. The run has no
  `stop()`: a method call cannot be taken back once sent. A service
  restarted by a reload starts its actions' runs afresh. A field and an
  action of the same name are a load error already, so the name is never
  both.

### 5.8 A command's output

(proc-lines, proc-streams, proc-reason, proc-keeper; decisions.md)
Every program strand reads, a `from listen` or polled command, an
action's, and a `file`'s `run` (section 9.7), is read the same way.

- **stdin** is `/dev/null`: a program that asks (pacman's `[Y/n]`,
  Python's `input()`) reads the end of its input at once, and its
  question stays visible as the open line. Give it its own flag
  instead (`--noconfirm`).
- **Two streams.** stdout and stderr are two pipes, both read, and each
  line keeps which it came on (`Line.stderr`), never made a severity:
  curl, git, wget, ffmpeg and `tail -F` write progress and notices to
  stderr, and `pacman -Qkk` writes warnings to stdout and exits 0. Lines
  of the two streams are in the order strand read them, which can
  differ a little from the order they were written (nothing orders two
  pipes); where it matters, a helper script writes `2>&1` and its lines
  all come on stdout. Fields and `line` events read stdout alone;
  stderr is why a run failed.
- **Framing.** Output is read as a terminal shows it:

  | Bytes | Read as |
  | --- | --- |
  | `\n`, `\r\n` | the end of a line |
  | `\r` not before `\n` | the line starts again and what follows replaces it, so a bar redrawn a hundred times is one line, its last drawing (a `\r` at the end of what was read waits for the next byte) |
  | `\b` | removes the character before it (a spinner) |
  | `ESC [ … final`, `ESC ] … BEL` or `ESC \`, `ESC` and one byte, any other control character but `\t` | removed (colour and cursor codes), in lines, in why a run failed and in a document alike; a `from file` is read as it is |
  | bytes that are not UTF-8 | U+FFFD, decided per line |

  A line no `\n` has ended yet is the **open line**: the last of an
  action's `lines`, `open` true, updated at most once a frame, and
  ended only by `\n` or the end of the output, never by a pause (wget
  prints `Connecting to … ` and `connected.` seconds apart, one line).
  Fields and `line` events read ended lines alone, so half a JSON line
  is never parsed. A line over 4 MiB is skipped for fields and events,
  with a warning, and kept in `lines` cut to 2000 characters and `…`.
  A blank line is kept in `lines` and is neither an event nor a merge.
  A line keeps its leading spaces in `lines` (pacman's `  -> `); a
  document and a field's text are trimmed, as before. A polled
  command's and a `-> T` call's output are framed the same way before
  they are read as one document, so a `-> text` from a program that
  redraws a bar answers with its last drawing; (lines-list) read as a
  list, such output (text, not JSON or XML) is these lines, an item
  each (section 5.6).
- **Buffering.** Most programs hold back their output when it goes to
  a pipe, until a buffer fills or they exit: C programs, Python, grep,
  sed, awk, jq. Strand gives no terminal (a pty would make the output a
  screen, merge the two streams, hang up on the command when strand
  exits and turn prompts on), so the remedy is the program's own:
  `stdbuf -oL -eL` for a C program, `grep --line-buffered`, `sed -u`,
  `jq --unbuffered`, `python3 -u` (or `PYTHONUNBUFFERED=1`), awk's
  `fflush()`, or a tool's own `--json` or `--progress`. (proc-permit)
  So `permit exec` sees through `stdbuf` and `env`: when a command's
  first item is `stdbuf` followed only by `-i`, `-o` or `-e` options
  (`-oL`, `-o L`, `--output=L`), or `env` followed only by `NAME=value`
  items setting the locale, the time zone, the terminal or Python's
  buffering (`LANG`, `LANGUAGE`, `LC_…`, `TZ`, `TERM`, `NO_COLOR`,
  `COLUMNS`, `PYTHONUNBUFFERED`), each a text literal, the program
  checked against `permit exec`, and by `check::shell_script`, is the
  one after them, so `permit exec "pacman"` allows `["stdbuf", "-oL",
  "pacman", …]` and `["env", "LC_ALL=C", "pacman", …]`, the two forms
  in either order. `stdbuf` and `env` are seen through as those bare
  words or as `/usr/bin/…` or `/bin/…`; at any other path the program
  is one that shares the name, and it is checked itself. Any other item
  (`env -i pacman`, `stdbuf --help`, a parameter) stops the seeing
  through, as does a variable that could change which program runs or
  what it loads (`env PATH=… pacman`, `env LD_PRELOAD=… pacman`), and
  the program checked is `stdbuf` or `env`.
- **Why a run failed.** A command that could not start, ended with a
  status its `ok` does not list (section 5.7) or by a signal, timed out
  or printed too much fails with a headline (``"`pacman` failed (exit
  status: 1)"``, ``"could not start `x`: …"``, ``"`x` timed out after
  10 s"``), which names the program past a leading `stdbuf` or `env`
  as `permit exec` sees through them (`["stdbuf", "-oL", "rsync", …]`
  fails as `` `rsync` ``; what could not start is the program strand
  started, `` `stdbuf` `` itself), and the reason follows it after
  `": "`: its stderr, framed
  and its blank lines dropped, whole up to 4 KiB, past that its first
  1 KiB and its last 3 KiB, each cut at a line, joined by a line `…`;
  when it printed nothing on stderr, the last 1 KiB of its stdout (a
  script that echoed why), but for a `from listen` command, whose
  stdout is the data it fed for as long as it ran (decisions.md
  proc-output). With neither, the headline is all. stderr is
  read for up to 100 ms after the program exits, so a child left
  holding the pipe never delays the answer. This one rule makes an
  action's `error`, a call's `.error`, a polled or listen command's
  diagnostic (`strand watch`), an action's notice and a `file`'s `run`
  notice: ``"`pacman` failed (exit status: 1): error: failed to commit
  transaction (conflicting files)"``; the conflicting files themselves
  are in the run's `lines`, since pacman prints them on stdout. Its
  first line is `rec.error?.split("\n")?.first`,
  which suits a program that says why first (pacman, rsync); one that
  prints progress on stderr before it fails (git, curl) leads with its
  progress, so read its own marker instead, the last line starting
  `fatal:` or `curl:`, or the error's last line. The lines themselves
  are `rec.lines.filter(l => l.stderr)`.
- **Logging.** A successful run's stderr goes to strand's log at debug
  level (at info for a non-zero status its `ok` lists, unless a value
  read printed only stderr, its failure, section 5.7); a failing
  `-> T` call is logged at info, an action's failing run at warning.
- **Rate and memory.** Reading never waits on the logic thread: lines
  are framed where they are read, kept (an action's last 1000 lines, at
  most 256 KiB) and published at most once a frame. Only `line` events
  wait for their handlers (section 5.6).
- **Outliving strand.** An action's command outlives strand (section
  5.7), and so do its pipes: a small keeper process, which strand starts
  the first time it runs a command action (`strand __keep`), holds them
  too. When strand exits, crashes or is restarted, the keeper reads what
  the command still prints, to its end, and drops it, so a command
  never dies of a closed pipe nor waits on a full one. After a restart
  the run is no longer this strand's: `running` reads false. A polled,
  listen or `-> T` command still ends with strand.

## 6. Trees

### 6.1 Elements and the call shape

- Every node is written `kind [positional] { props; children }`, for
  builtin elements and components alike. The positional is one
  expression; it fills the element's positional prop (for `text`, the
  text; for `image` and `icon`, the source) or a component's first
  parameter. Setting a prop both as the positional and in the block is a
  load error.
- A head argument written `name: expr` is the first prop:
  `pages current: page { … }` is `pages { current: page; … }`.
- Which element kinds exist, which props and events each accepts, and
  which children it may hold are schema entries. An unknown element is a
  load error with a did-you-mean that includes the tree keywords
  (`whn` → `when`).
- **Selectors.** In an `svg` element, `#name { props }` applies props
  to the SVG element with that id.
- **Local files.** The file an `image`, `svg` or `lottie` draws is
  found as settings files, service files, shaders and templates are: a
  relative path (`svg "gauge.svg"`, `image "icons/wifi.svg"`) is
  resolved against the config directory, in any module, never against
  the directory Strand was started from; `~/…` is in the home
  directory; an absolute path or a `file://` URL is used as written.
  This holds for a computed source too. An `image` source is a path
  when it starts with `/`, `~/`, `./` or `file://` or ends in `.png`,
  `.jpg`, `.jpeg`, `.svg`, `.gif`, `.webp` or `.apng`; anything else is
  an icon name. `strand check` warns (`check::missing_file`) when a
  literal path names no file; an icon name and a computed source are
  not checked. While the shell runs, saving a file a mounted `image`,
  `svg` or `lottie` draws (by its source's current value, a computed one
  too) draws it again within a frame or two: the config is not
  reloaded and no state changes, and the old drawing stays until the
  new one is read. A file a Lottie names beside it is read again only
  with the Lottie file (decisions.md m6-owner-fixes).
- **Icon names.** An icon name (an `icon`'s source, an `image` source
  that is not a path, and so every app, window and tray item icon a
  config draws by name) is looked up first in the config directory's
  `icons/` folder, then in the icon theme (the Icon Theme
  Specification). The folder is flat: `<name>.svg`, else `<name>.png`;
  its subdirectories are not looked in, and an SVG is drawn at any size
  and a PNG scaled. A name's candidates are the name, its other
  `-symbolic` variant, then the same for each generic fallback (a
  trailing `-segment` removed); for each name and its variant the
  folder comes before the theme, so `icon "wifi"` draws
  `icons/wifi.svg`, else `icons/wifi-symbolic.svg`, else the theme's
  `wifi` or `wifi-symbolic`, and only then a fallback. A folder file
  whose name ends in `-symbolic` is recoloured by `color` (by default
  the scope's `$fg`) as a theme's symbolic icon is; any other is drawn
  as authored. Adding, editing or removing a file there redraws every
  icon while the shell runs.

### 6.2 Props and inherited props

- A prop is `name: value`, ended by `;` or a line break. Each prop's
  value is a live expression (section 8.1).
- A prop with several values takes commas: `margin: 8, 8, 0`. Insets
  (`pad`, `margin`) take one to four values read as in CSS: one for all
  sides; two for vertical then horizontal; three for top, horizontal,
  bottom; four for top, right, bottom, left.
- Space-separated groups (`font: "Inter" 13px 500`, a shadow list
  `0 8px 24px $a, 0 1px 2px $b`) are accepted only by font and shadow
  props; elsewhere they are a load error suggesting commas.
- **Inherited props** (`font`, `weight`, `color`) set on any node
  apply to every descendant that does not set its own. These three are
  the only inherited props.
- **Markup** (decisions.md doc-formats). A `text`'s `markup:` says how
  tags in its text show: `none` (the default) as written; `basic` as the
  freedesktop notification markup (`b`, `i`, `u`, `a`, `img`'s alt, other
  tags kept as text); `html` as an HTML fragment (blocks as line breaks,
  lists marked, inline styles, links in `$accent`, scripts, styles and
  unknown tags dropped). Both decode HTML's character references. An
  `input` ignores it.

### 6.3 Conditional style

- `when cond { props }` applies its props while `cond` is true; when it
  turns false, those props return to the values they would otherwise
  have. A `when` block holds props and its element's event handlers
  (`on click`, `on key`, …); a child, an `on change`, a service's event,
  a timer or other item in it is a load error. A handler in a `when` runs
  only while the condition holds; with it false the event goes on out as
  if the handler were not there, and a key claim claims nothing (section
  6.7). (decisions.md keyboard)
- **Source order wins.** When several `when`s, or a `when` and the
  node's own props, set the same prop, the one written last among those
  that apply wins, as in CSS. There is no other precedence.
- `hover`, `pressed`, `focused` and `selected` are booleans of the
  **enclosing node** (the node the `when`, `if` or expression is
  written in). `hover` stays true on a pressed node while it is dragged,
  even when the pointer leaves it.
- A node's `hover` is true while the pointer is over it or over one of
  its descendants on the same surface. A `popup` is a surface of its
  own: the pointer on a popup does not hover the element it is anchored
  to. A popup that opens or grows under a pointer that has not moved,
  resting on the surface it opens from (directly or through the popups
  between), is under the pointer at once, as if it had moved (a
  compositor may wait for the next motion to say so; decisions.md
  m6-owner-fixes). Over any other surface (a sibling popup, another
  bar) the pointer is the compositor's until it moves.
- `hover` and the cursor follow what is under the pointer as the last
  frame drew it, also when what moved is the content and not the
  pointer (a list scrolled, a row closed, an animation), a frame later
  at most. A press held keeps the node it went down on. A still pointer
  always lets a surface come to rest: under it `hover` makes one move,
  from one node to another, at most twice, until the pointer moves, a
  wheel, button or key comes, or `hover` has made no move for a second.
  What moves elsewhere on the surface does not count. So
  a node that moves itself off the pointer when hovered (`when hover {
  y: -10 }` with the pointer in the strip it leaves) flips a few times
  and stays hovered, and a node that slid away and back loses its
  `hover` and takes it back. A surface pays for this only with the
  pointer on it, and only a frame that moved a hit box routes it again.
  (decisions.md still-pointer)
- **`trigger: hover`** on a `popup` gives its open state to the pointer.
  It opens while the pointer is on the element it is anchored to, after
  its `delay` (none by default). It stays open while the pointer is on
  that element or on the popup, popups opened from inside it included,
  or while a press that went down on it is held (a slider's drag), and
  for its `grace` after the pointer leaves them (200 ms by default), so
  the pointer can cross the gap. It never takes the keyboard. One
  `trigger: hover` popup is open from a surface at a time: when another
  opens from the same surface (the pointer went straight to the next
  bar item), the open one closes at once. Its `enter` and `exit` poses
  play as it opens and closes. Its `open:` opens it from code: while
  that is true it is open whatever the pointer does (opening at once,
  without its `delay`, and closing another opened from the same
  surface), and once it is false the pointer holds it as above, so it
  closes after its `grace` unless the pointer is on it or its element
  (decisions.md m6-owner-fixes). That `open:` is never two-way: what
  shows is `p.open`. `trigger`,
  written on the popup itself, is `open` (the default: `open:` decides)
  or `hover`; anything else, and `delay` or `grace` without `trigger:
  hover`, is a load error.
- `p.open` reads the open state of the popup (or other surface) with
  `id: p` (an `id:` on a surface names its root, `panel P { id: p …
  }`): true from the moment it opens until it closes, as its exit
  pose starts, whether `open:` or the pointer opens it; false on other
  elements. `when p.open { … }` styles the anchor while its popup
  shows.
- To read another node's booleans, give it `id: name` and read
  `name.hover`. An `id:` name is visible across the whole component or
  surface that holds the node. A node's props are never assignable
  through its id (section 8.3).
- `self.width` and `self.height` read the enclosing node's laid-out
  size, for container queries: `when self.width < 300 { … }`. A query
  switches with 4 px of hysteresis, so it cannot flicker, and costs at
  most one extra layout pass per frame. An element whose `width` or
  `height` is read through `self` or its id is measured from its mount,
  so a first read in a handler, or as a popup mounts, finds its size once
  it has been laid out: a popup's `on show` finds its anchor's and its
  surface's. A popup's own content is not laid out yet in its own `on
  show` and reads 0 there, and a size read through a value passed
  elsewhere is measured only from that first read, so that read gives 0
  too (decisions.md first-read).
- **`name.box`** reads the laid-out box of the node with `id: name` as
  a `Rect` (`x`, `y`, `width`, `height`), in logical pixels from the
  top-left corner of its surface's box (a shadow's overhang lies
  outside it), where layout put it: its paint offsets (`x`, `y`),
  transforms and poses are not in it. A popup's own `box` is where it
  sits on the surface it opens from; a bar's, panel's, OSD's or lock's
  is at 0, 0. A bar on each output is its own instance, so the numbers
  are the same at every scale. The box follows layout a frame late: it
  reads all zeros until the node is first laid out, and that first box
  is taken at once (a value following it does not spring in from 0,
  0); after that a value following it springs like any value, `x:
  cur.box.x - ws.box.x ~ $motion.spatial`. A box that does not move
  costs nothing. (decisions.md m6-w2-surface, 2026-10-14)
- **`self.pointer`** (or `name.pointer`) is where the pointer is in the
  node's laid-out box, a `Point` (`x`, `y`, logical pixels from the
  box's top-left corner), or null while the pointer is not over it or
  one of its descendants on the same surface. Its paint offsets and
  transforms, and its ancestors', are undone as the frame drew them, so
  a rotated knob reads it upright. It changes at most once a frame
  however fast the pointer moves, and also when the node moves under a
  pointer that stays still (a `scroll` scrolled, a layout or an
  animation): it is where the pointer is in the box as the frame laid
  it out. While a left-button press that went down on the node is held
  it keeps a value wherever the pointer goes (off the node, off the
  surface), measured in the box as it was when the press went down,
  the surface's place included: a drag that moves the node (its `x`,
  its width) or its surface (margins from state) moves the pointer in
  that frame, never the frame, so it cannot feed back. A press's
  `pointer` is set before its `pressed`, so `on change self.pressed {
  grab = self.pointer }` reads where it went down. A knob is
  `atan2(p.y - cy, p.x - cx)` (between -180° and 180°: section 7.2's
  `atan2`); a resize grip adds the pointer's travel since the press to
  the width it had. Outside a press `pointer` is measured in the node's
  current box, so a node whose place or size follows its own `pointer`
  moves the frame it is read in; it changes at most once a frame and
  the checker does not refuse it, but such a node should read the
  pointer of a parent that stays put (the dock reads its row's).
  (decisions.md flex, 2026-10-24)
- **`name.blank`** is true while the `thumbnail` with `id: name` has
  nothing to show and draws nothing: its window went, its screen could
  not be captured, or, inside a `lock`, its monitor has no still from
  before the lock (it was plugged in while locked). It turns true a
  frame after the thumbnail is first drawn and false when a frame
  comes, and is false on other elements: `thumbnail screen { id:
  still }`, then `when still.blank { … }` styles a monitor whose lock
  has no still of its own way (decisions.md oi-lock, 2026-10-26).
- **What a box may drive.** Anything that does not lay that box out
  again. The checker follows what each value depends on, directly or
  through `let`s, the `state`s and service fields handlers set from
  it, `fn`s, component parameters, `for` bindings and conditional ids
  (the conditions that pick the node), and refuses every loop, however
  many bindings and surfaces it passes through (`check::box_layout_loop`,
  which shows the loop's path). What a binding lays out follows from
  what it sets: paint props (`x`, `y`, `opacity`, colours, transforms)
  lay out nothing, nor do a surface's effects (`bg`, `opacity`, `shadow`,
  `blur`, …), corners and `open`; the size of an element that is always
  `place: absolute` (no `when` or pose changes its `place`) lays out it
  and what is inside it; any other layout prop, an `if`, `for`, `match`,
  `pages`' `current`, a `segmented`'s `options`, a `set { $token: … }`
  and a `when { id: … }`'s condition lay out their whole surface, and a
  surface's own size and placement also the popups opened from it; a
  `bar`'s size, `edge`, `margin`, `open` and `screens` (its exclusive
  zone), and what lays out a bar sized by its content, lay out every
  `bar`, `panel` and `osd`; a component's or file's tokens reach every
  surface. What lays out a popup's own box lays out what the popup
  holds too, and the popups inside it: inherited values (a `set`,
  `font`, `weight`, a surface's own props) reach into the popups nested
  in what they set. So a popup may be sized from the bar item it opens
  from, unless that item is sized from the popup; two absolute boxes
  may not each be sized from the other.
  `name.width` and `name.height` of another node arrive a frame late
  like `name.box` and are followed too, but they loaded before `.box`
  (section 14): a loop through them with no `.box` on it is a warning,
  `check::size_loop`, naming the path, and still loads (a node's own
  size, in its own props, stays a container query). A box read through
  a node passed as a value counts as any box: it may drive only what
  lays out nothing.
- **Conditional ids.** `id: name` in a `when` block names the node
  while the condition holds: `for n in ids key n { box { when n ==
  current { id: cur } } }` names the current copy, read outside the
  `for`. Several `when`s, on one node or on several, may give the same
  name; while several hold, it names the node whose condition started
  holding last, and the one before when that one's stops. While none
  holds, the name reads a node that is never laid out (its booleans
  false, its box zeros). A name that already means something where the
  `id:` is (a plain `id:`, a `state`, a parameter, a variant, a
  builtin) keeps that meaning, and the `when`'s `id:` does nothing, as
  it did before conditional ids, with a warning
  (`check::conditional_id_ignored`). The nodes a conditional id may
  name are measured for what is read through it, so a value following
  `name.box` travels from one box to the next.
- **A travelling island** is one popup and these reads, with no other
  construct. The popup anchors to the whole group of items, is sized
  from it (another surface's box) and draws nothing itself, so only its
  island takes input (section 6.7); the island follows the hovered item:

  ```strand
  state at = "vol"
  bar Top {
    row {
      id: pill
      icon "audio-volume-high" { id: vol; when at == "vol" { id: it } }
      icon "network-wireless" { id: net; when at == "net" { id: it } }
      on change vol.hover { if vol.hover { at = "vol" } }
      on change net.hover { if net.hover { at = "net" } }
      popup {
        id: pop; trigger: hover
        width: pill.box.width + 16; height: 220
        col {
          place: absolute; bg: $surface; radius: 12; height: 200
          x: it.box.x - pop.box.x - 8 ~ $motion.spatial
          width: it.box.width + 16 ~ $motion.spatial
          if at == "vol" { text "Volume" } else { text "Network" }
        }
      }
    }
  }
  ```

### 6.4 if, else and match

- `if cond { children } else { children }` mounts the first block's
  children while `cond` is true and the `else` block's otherwise.
  `else if` chains. Unlike `when`, it adds and removes nodes: a removed
  subtree plays its `exit` pose (section 6.6), then unmounts, and its
  handlers are cancelled and its service subscriptions stop.
- `match value { pattern => children, … }` mounts the arm whose pattern
  matches, by the same rules (section 7.3).

### 6.5 for and keys

- `for x in xs { children }` mounts the block once per item of `xs`,
  with `x` in scope. There is no capacity: every item gets its copy.
- Each copy is identified by its item's **key**. Service items and
  keyed collections bring their own (a workspace by its `id`, a
  notification by its `id`). For plain data, write `key e`:
  `for p in pins key p.app { … }`. A `for` over plain data without a
  key is a load error. A key is an identity, not an equality: a number
  key keeps its unit, so `2px` and `2ch` are two keys although
  `2ch == 2px` (section 7.2). `int` and `float` are not units: `3` and
  `3.0` are one key, so a key computed by arithmetic finds its item
  whichever of the two it is (decisions.md dictionary).
- When `xs` changes, copies whose key stays are kept with their state
  and move to their new place (they glide there, section 6.6); copies
  whose key goes play `exit` and unmount; new keys mount and play
  `enter`.
- `state xs: [T] key f = []` declares a keyed collection: each item's
  key is its field `f`. Handlers change it with `push`, `insert`,
  `remove_key`, `move` and `update`. `remove_key` of a key the
  collection does not hold does nothing, so forgetting an item is safe
  to repeat; `move` and `update` of one are an error of the handler
  (section 8.3), as `push` and `insert` of a key it already holds are.
  `.filter`, `.map`, `.take`, `.sort_by` and `.fuzzy` on a keyed
  collection or a service list keep keys and update incrementally.
- `xs.get(k)` reads the item whose key is `k`, or `null` when there is
  none: `tray.items.get(id)`, `pins.get(app)`. It is for keyed lists: a
  service's (by its items' own key), a `state`'s with `key f`, and a
  view `let` or chain over one (`pins.filter(…).get(app)`, by the
  `state`'s `key`). `k` has the key's type, and a binding over
  `xs.get(k)` follows the collection. `get` on a list with no key is a
  load error (`check::missing_key`). `xs[i]` stays a position on every
  list: a key never goes in a list's brackets (decisions.md
  dictionary).
- A dictionary's `m.entries` is keyed by each entry's `key` (section
  7.1): `for e in m.entries { … }` keeps a row per key across writes. A
  changed value updates its row, a new key mounts at its place in key
  order, and a removed key's row plays `exit`.
- Nothing bounds a collection for you: there is no capacity and no
  eviction. A collection that must stay small is bounded where it is
  written. A dictionary is pruned by liveness, in the handler that
  writes it: `used = used.filter(e => windows.all.any(w => w.id ==
  e.key))`. A recency list stays a list, bounded by `take`: `recent =
  ([t] + recent.filter(s => s != t)).take(8)`. Prune when you write,
  not on a service's first report: `on change` takes the first value as
  its baseline, and a service may first report an empty list
  (decisions.md dictionary).
- A `list` container lays out and mounts only its visible rows
  (virtualisation is the container's job, not the loop's).
- Rows that change above a `list`'s view keep the rows in view where
  they are: a reader's place holds. At the list's top, or scrolling
  back to it, there is no place to keep: it stays at its top and a row
  added above the first shows. (decisions.md list-top)

### 6.6 Poses, transitions and keyframes

- **Every visual prop springs.** When a prop's value changes, the node
  animates to it. Movement and size use `$motion.spatial`; colour and
  opacity use `$motion.effects`. A spring retargeted mid-flight keeps
  its velocity.
- **`~` overrides the transition** for one prop:
  `width: 24 ~ $motion.bouncy`, `~ 200ms`, `~ instant`,
  `~ ease(out_back, 300ms)`, `~ bezier(0.05, 0.9, 0.1, 1.05)`. In a
  `when`, the override applies while that `when` wins. A change takes
  the transition in effect after it: the `~` expression is evaluated
  with the value, so `opacity: open ? 1 : 0 ~ (open ? 160ms : 1s)`
  fades in over 160 ms and out over 1 s, as the `when` form does.
  A change of the transition alone moves nothing.
- **What cannot interpolate snaps**: fonts snap, shadow lists are padded
  to equal length and spring, layout lengths (`pad`) snap while paint
  offsets spring. A `graph`'s value snaps (a `~` on it changes
  nothing): `smooth` eases it, and each column is its value at that
  column's tick on the boot clock, not a spring's position at whatever
  frame drew it (decisions.md graph-follow; section 14). With the desktop's reduced-motion setting on, every
  transition snaps and loops, time signals and effects stop. A focused
  `input`'s caret stops blinking too (section 6.7).
- **Paint-only props** (`x`, `y`, `scale`, `rotate`, `opacity`) never
  cause layout. A size spring relays out only the subtree under the
  nearest ancestor whose size does not change.
- **`enter { props }`** is where a node animates in from: on mount it
  starts at those values and springs to its own. **`exit { props }`** is
  where it animates to before it unmounts; without one, `exit` mirrors
  `enter`. Poses apply to surfaces, `if` branches, `for` copies, list
  items and pages. Siblings of a node that is added, removed or moved
  glide to their new places. Each glides on the `$motion.spatial` in
  effect where it is, so `set { $motion.spatial: spring(520, 0.78) }` in
  a row (section 9.4) gives its children's glides that spring; a
  `drag:` source let go springs back, and a wheel step moves a `scroll`
  or `list`, on the one in effect at it. While a content-sized
  surface's box springs over a step of its content, what moves in it
  glides with the box, on the box's curve, what the change that starts
  the step moves included (decisions.md glide-curve).
  A `popup`'s contents mount each time it opens, so their `enter`
  poses play at every open, which a stagger on open relies on. A popup
  that starts out looking like something already on screen would
  flicker: leave the pose out, or skip it by a value, `enter: still ?
  none : fade`, or `enter { x: still ? 50 : 200 }` for a node whose own
  `x` is 50 (decisions.md popup-enter).
- **`keyframes name { 0%, 100% { … }; 50% { … }; duration: T }`**
  declares a timed animation; `play name` in a handler plays it once on
  the enclosing node.

### 6.7 Layout and input

- **Flex layout first.** `row`, `col`, `stack`, `grid`, `scroll`,
  `list`, `split` and `spacer` are containers; flex props and
  `min_*`/`max_*` apply. `place: absolute` takes a node out of the flow,
  placed by `x` and `y`.
- **A stack puts its children over each other** in one cell its size:
  a `stack`, a `box` and a surface (a `popup` included) lay out their
  children so. Its `align` places every child on both axes (`start`,
  `center`, `end`, or `stretch` to fill); by default a child fills the
  cell on an axis where it has no size and sits at the start of one
  where it has. There is no alignment per child: a child placed apart
  from its siblings goes in a `row` or `col` that fills the cell and
  places it (`row { justify: end; … }`), or is `place: absolute` at
  its `x` and `y`.
- **`split`** has three parts, `start`, `center` and `end`; `center` is
  centred on the split whatever the other two hold. `start`, `center`
  and `end` are only valid in a `split`.
- **Shrinking.** In a full row or column, children give way by `shrink`
  (a flex factor, default 1). An `image` or `icon` sized in absolute
  lengths (`size`, `width` or `height` in px or `ch`, none a percentage)
  defaults to `shrink: 0`. An explicit `shrink:` overrides either
  default.
- **Hit testing** follows the node's rounded shape where it is drawn
  (its paint offsets and transforms, and its ancestors', move it; a
  slider or `segmented` reads the pointer there too, so a slider turned
  by `rotate` follows the pointer along its drawn track). `hit: grow(n)`
  enlarges it by `n` for small targets; `hit: none` takes no input in
  the node's own box (the pointer passes through to what is below),
  while its children take theirs and are hit with it among their
  ancestors. What is below a node is its parent, whose own box takes
  the pointer unless it has `hit: none` too; on a surface's root the
  pointer leaves the surface for what is behind it, by its input
  region, wherever none of its nodes takes input (a `panel`, `bar`,
  `popup` or `window`; a `lock` never, and an `osd` takes none anyway).
  The region is each hit box's bounds, so a rounded corner of one still
  stops the pointer, and while a press that went down on the surface is
  held it takes its whole box. A `hit` set by a `when` takes effect at
  its next frame, whether or not anything else changed, and that frame
  repaints nothing. (decisions.md hit-through) A node at `opacity: 0` is not drawn and not hit, its
  children neither: a control that takes input unseen keeps its
  opacity and draws nothing (`color` and `track` of alpha 0, no `bg`).
  Shadows enlarge the buffer but not the input region. A `panel`'s or
  `osd`'s buffer keeps, from its first frame, room on each side for the
  farthest any shadow, glow or fillet on it reaches, every `when`'s
  shadow counted (a box whose size or place may spring, by a `~`, a
  pose, or a size bound or set in a `when`, taken at any edge of it); the room only grows
  until a reload. A `bar` takes a lifted shadow's room while it shows
  and gives it back at rest (decisions.md shadow-buffer).
- **`wrap: true`** on a `row` or `col` runs its children on in another
  row (column) when one is full. The lines pack at its start, `gap`
  stands between lines as between children, and `align` and `justify`
  place the children within each line; a column wraps only when its
  height is bounded. (decisions.md flex, 2026-10-24)
- **A `scroll` scrolls along `axis:`** `vertical` (the default),
  `horizontal` (its children in a row) or `both` (each child its own
  width). A wheel notch with no sideways motion scrolls a horizontal
  one under the pointer only when no scroll there can move along y (a
  strip inside a page leaves it to the page); a touchpad's vertical
  swipe never does. A wheel event moves one axis, the one it moves most
  along; a touchpad gesture keeps the axis and the scroll its first
  event took until the fingers lift (on `both`, a diagonal swipe moves
  one axis, not each in turn). `snap: true` on a
  `scroll` or `list` settles a wheel step and a touchpad's lift with a
  child's start (a row's, for a list, mounted or not) where the first
  child starts at rest, or at the content's end: a notch moves to the
  next child, fingers resting between two settle on the nearer, and a
  fling lands on the child nearest where it would have stopped. Fingers
  still on the touchpad move it freely. (decisions.md flex, 2026-10-24)
- **Sliders and meters laid out taller than wide run upward**: a
  `slider` or `meter` whose box is taller than it is wide (`width: 24;
  height: 160`) has its track upright, its value growing from the
  bottom, and a drag reads the pointer's height; an upright meter
  fills plainly (its `wave` is a horizontal meter's). Its written
  `width` and `height` decide (where both are lengths), else its
  laid-out box, so a box springing through a square does not turn it;
  one that grows from a written 0 on one axis (`width: 0; grow: 1`,
  sharing what is left of its row) runs along that axis, whatever its
  other side,
  and a drag keeps the orientation it began with. There is no
  orientation prop. `step:` on a slider moves a drag in whole steps of
  its `range`'s units from its low end (`range: 0, 100; step: 5`), the
  knob and the value written alike; the value written is the decimal
  the step and the low end spell (`range: 0, 1; step: 0.1` writes
  `0.9`, never `0.90000004`). (decisions.md flex, 2026-10-24)
- **Focus.** `input`, `list`, `button`, `slider` and `segmented` are
  focusable, and so is any element with a `focus:`, whatever its value. A
  surface that takes the keyboard focuses its first node with `focus: true`;
  `focus:` is reactive, so when it turns true on a node of a surface that has
  the keyboard, focus moves there. `node.focus()` moves it from any handler,
  on any element, in order with the other asks of that tick (below); on a
  surface without the keyboard it waits for the keyboard. Tab and Shift+Tab
  move focus between the surface's focusable nodes in tree order, round from
  the last to the first, skipping `hit: none` and those not shown (at
  `opacity: 0`, theirs or an ancestor's, or playing their exit pose, as a
  page going away does). A `list` is one stop: what is in its rows is one only
  with a `focus:` written. Focus on a node that stops being shown or taking
  input moves on as Tab would, or to the surface on one closing or with
  nothing else, so a key neither presses it nor types in it; it comes back when
  the node shows again, unless focus moved on meanwhile. A left press focuses the `input`, `list` or node with
  a `focus:` under it, or else a `button`, `slider` or `segmented` under it
  unless an `input` or `list` has focus, which keeps the keys: a launcher's
  button runs and the typing stays in the field. A press before the keyboard
  comes, on one of those three, does not beat a `focus: true` when it does. Tab
  is a default that a claim
  takes over: `on key "tab" { … }` on the focused node or one around it runs
  and focus stays (it moves focus itself with `focus:`). An `on key(k)` only
  hears Tab, and focus moves. Ctrl, Alt or Super held leave Tab alone. A
  surface that closes lets its focus go, as when the keyboard leaves it. Focus
  moved by anything but a press shows the node, as `node.reveal()` does: a
  press leaves what is under the pointer where it is. (decisions.md flex,
  2026-10-24; keyboard)
- **Keys of what is focused.** Each is a default a claim takes over, and Ctrl,
  Alt or Super held leave them alone.
  - Return or space on a focused node runs its own `on activate` if it has an
    active one, else `on click`, which goes outward as a pointer's does; on a
    node in a `list`'s row the row is selected and its `on activate` runs too,
    and on the row itself its `on click` and then `on activate`, the list's if
    it has none, as a pointer's click there. A repeat does nothing: holding it is not many clicks. An `input` and a
    `list` have their own Return, an `input` with a `nav:` list its list's, and
    the surface itself has none. One press of Return is one `on activate` on
    them too: a repeat fires nothing, and a shell wanting repeats uses a timer
    (decisions.md robustness). Space and Shift+space page a focused `scroll` or
    `list` forward and back, as the Page keys do, repeating, and go to no click.
  - A `slider` bound two-way: Left and Down step down, Right and Up step up,
    Page keys ten steps, Home and End go to the ends. A step is its `step:`,
    else a hundredth of its `range`. It writes as a drag does, the decimal the
    step spells; keys queued while logic is busy all count.
  - A `segmented` bound two-way: Left and Right choose the option beside the
    chosen one, stopping at the ends.
  - A `scroll` with a `focus:`: arrows step 40 logical pixels along the ways it
    runs (Up and Down go along x on one that runs only that way, as a wheel
    does), Page keys go a view, Home and End to the ends, each springing as a
    wheel step.
- **`arrows: focus` on any element** makes arrow keys inside it move focus to
  the focusable node nearest that way by their laid-out boxes: of those wholly
  past the focused node's edge, first those level with it, then the smallest
  gap, then the middle nearest, then tree order. With nothing that way, focus
  stays; `arrows: focus_wrap` goes instead to the far end among those level
  with it. It is scoped to the nearest element around the focused node with an
  `arrows:`, and does not reach into another such element inside it or out of
  it, so Tab crosses between them. An element that uses an arrow keeps it: an
  `input` Left and Right for its caret, and Up and Down with a `nav:`; a
  `list`; a `slider` and a `segmented`'s Left and Right, bound two-way; a
  `scroll` along the ways it runs. The other arrows move focus, and if nothing
  is that way they do what they would have. A container that is focused itself
  goes to its first. A claim beats it. (`wrap: true` is taken: on `row` and
  `col` it wraps their children. decisions.md keyboard.)
- **A scroll from code.** `s.scroll_y` and `s.scroll_x` read how far a `scroll`
  or `list` is scrolled, as drawn, a frame behind and reactive: render reports
  them only for a node they are read of, and only when they change, so a read
  wakes nothing at rest. An `on change` of them is input, as of `selected`.
  `s.scroll_to(y)` springs there, kept within the content (a `snap: true` one
  to the nearest child); `s.scroll_by(dy)` springs by that much from where it
  is heading, as a wheel step. Each takes `x:` or `dx:` too; `y` alone on one
  that runs only along x is along x. `node.reveal()` on any element moves every
  `scroll` and `list` around it, the innermost first, as little as it takes to
  show it, at once, as a list's selected row. These are asks, as
  `results.next()` is: in the tick's order, and a position or a reveal waits
  for the layout of the diff it came with, so it sees what that diff mounted,
  though not a size still springing there. `scroll_to` and `scroll_by` on an
  element `strand check` can see does not scroll are the error
  `check::not_a_scroll`; through `self` or a conditional id they do nothing,
  and the first says so to `strand watch`. (decisions.md keyboard)
- **A pattern claims a key.** `on key "ctrl+n", "down" { … }` runs for
  those keys, the patterns string literals, an optional `(k)` after them
  (`on key "esc" (k) { … }`). The router looks from the focused node out
  to its surface root, the innermost first, before any default and any
  other handler; the first active claim of the key takes it. Its handler
  alone runs, and the key's defaults (typing, a list's keys, Return,
  Tab, Escape closing) and every other handler, `on key(k)` observers
  included, do not. On one element, the last written active claim wins,
  as among `when`s. Claims fire on repeats too. A drag's Escape stays the
  drag's: it cancels the drag first. A claim sits directly on its
  element or in a `when` there, as every element event's handler does: in
  an `if`, `for` or `match` body it is a load error, since those bodies
  have no element.
  - `propagate()` in a claim passes the key to the next enclosing active
    claim of it. The default stays stopped: the router has stopped it
    before logic hears of the key.
  - The active patterns are a reactive prop of the node, since logic runs
    on another thread and cannot answer "handled" in time. So a key
    arriving in the same tick as a change of a `when` is judged by the old
    value. A claim whose `when` is false by the time its body would start
    (keys queued while logic was busy) does not run; its key is spent.
  - **Patterns.** Modifiers `ctrl`, `shift`, `alt` and `super`, joined with
    `+` before the key, each once, in any case, and exact: `"n"` is not
    Ctrl+N. A letter is `"a"`, which is not Shift+A, or `"shift+a"`. A single
    other character (`"?"`, `"1"`, `"+"`) is the text the key types, and
    ignores Shift; `shift` on one is a load error (`"shift+1"`: write what it
    types, `"!"`).
    A longer name, in any case, is one of: the short names `esc`, `enter`
    (Return and the keypad's), `tab` (and `shift+tab` matches
    `ISO_Left_Tab`), `space`, `up`, `down`, `left`, `right`, `home`, `end`,
    `pgup`, `pgdn`, `backspace`, `del`, `ins`, each with its keypad twin where
    it has one; these xkb names: `Escape`, `Return`, `KP_Enter`,
    `ISO_Left_Tab`, `Page_Up`, `Page_Down`, `Prior`, `Next`, `Delete`,
    `Insert`, `Menu`, `Print`, `Pause`, `Scroll_Lock`, `Caps_Lock`, `Num_Lock`,
    `Shift_Lock`, the modifier keys (`Shift_L`, `Control_L`, `Alt_L`,
    `Super_L`, `Meta_L`, `Hyper_L` and their `_R`), `ISO_Level3_Shift`,
    `ISO_Level5_Shift`, `ISO_Next_Group`, `ISO_Prev_Group`, `Mode_switch`,
    `Multi_key`, `Begin`, `Undo`, `Redo`, `Help`, `Find`, `Cancel`, `Select`,
    `Execute`, `Break`, `Sys_Req`, `Clear`, `Linefeed`, `F1` to `F35`, `KP_0`
    to `KP_9`, `KP_F1` to `KP_F4`, `KP_Begin`, `KP_Add`, `KP_Subtract`,
    `KP_Multiply`, `KP_Divide`, `KP_Decimal`, `KP_Separator`, `KP_Equal`,
    `Muhenkan`, `Henkan`, `Hiragana`, `Katakana`, `Hangul`, and the ASCII
    punctuation's (`slash`, `question`, …); and any name starting `XF86` or
    `dead_`, taken as written and not checked. Anything else is a load error
    naming the closest, as are a pattern that is not a literal, an unknown or
    repeated modifier, and a stray `+` (`"++"`, `"+a"`).
    A key matches by its name. When the pattern holds Ctrl, Alt or Super it
    also matches by the key's Latin fallback, as an input's shortcuts do, so
    `ctrl+n` works on a Russian layout, and a plain `"j"` leaves the Cyrillic
    letter on that key to be typed (a letter also matches what the key types,
    so `"я"` is that key under `ru`).
  - **Around a password.** A claim of a key that types (no Ctrl, Alt or
    Super on a letter, a character or `space`) on or around a `type:
    password` input, or around any `input` in a `lock` or in a component
    a `lock` calls, is a load error (`check::claim_around_password`), even
    in a `when`: it would eat what is typed there, and a lock that cannot
    be typed into cannot be left. What a call gives a `slot` in the
    component's body counts as around.
    (decisions.md keyboard)
- **`on key(k)` observes.** It hears each press and repeat (`k.repeat`) on
  the focused path that no claim took, whether or not a default then
  takes the key too. `on key_release(k)` hears a key let go the same way,
  and claims nothing; it hears a claimed key's release too.
- **`cursor:`** sets the pointer's shape over a node, one of
  `CursorShape` (the CSS cursor names in snake_case: `default`,
  `pointer`, `text`, `crosshair`, `grab`, `grabbing`, `move`,
  `not_allowed`, `wait`, `progress`, `help`, `ew_resize`, `ns_resize`,
  `col_resize`, `row_resize`, `nwse_resize`, `zoom_in`, …). The
  innermost node under the pointer that has one decides; while the
  left button is held, the chain it went down on does, so `when pressed { cursor:
  grabbing }` holds while the drag leaves the node. An `input` without
  one shows `text`; anything else shows the default arrow. It is set
  through `wp_cursor_shape_v1`, or from the cursor theme where the
  compositor lacks it, and set again only when it changes, including
  when a prop changes under a pointer that has not moved. (decisions.md
  flex, 2026-10-24)
- **A `trigger: hover` popup that draws nothing itself** (no `bg`,
  border, shadow, `blur` or `backdrop` of its own) takes input only in
  the boxes of its top-level elements that draw (a `blur` or `backdrop`
  counts), as they are drawn this frame: the pointer passes through the
  rest of it to what is below. A travelling island (section 6.3) moves
  inside a popup wider than it, and only the island takes the pointer.
  A top-level element with `hit: none` gives its children's boxes
  instead of its own.
  While a press that went down on it is held (a slider's drag), it
  takes its whole box. Any other popup, unless its root has `hit: none`, takes the pointer in its whole box, gaps included.
  (decisions.md m6-w2-surface, 2026-10-14)
- **Events go to the innermost node with a handler** for them.
  `propagate()` in a handler passes the event on to the next enclosing
  handler.
- **`nav: id`** on an `input` routes arrow keys to the list with that
  `id`; Return activates the selected row (`on activate`). It names the
  list as it is once each change is done: one that mounts later (in an
  `if` that turns true), in the same change that points `nav` at it
  (`nav: m == b ? lb : la` beside `pages current: m`), or again when its
  page comes back, gets the keys, its first row selected; while it is
  not mounted the keys go to no list (decisions.md nav-remount). The
  selected row is scrolled into view as little as it takes (to its top
  if it is taller than the list's view), and kept in view until the
  pointer scrolls the list: when the list's view changes size, the row
  is brought into view again from where the view was before it was
  selected, so a list laid out shorter than its row (a filtered list
  whose height follows its rows, back from no results) shows its first
  rows again once it grows (decisions.md list-scroll-regrow).
- **A `list`'s selection from code.** `results.next()`, `.prev()`,
  `.first()`, `.last()`, `.select(i)` and `.activate()` are actions, for any
  handler, and do what the keys do: the same `selected` row, scrolled into
  view, a row past the mounted window included, and Return's activation
  (`on activate` of the selected row, the first row shown with no selection,
  or on landing for a row on its way). From no selection `next()` and
  `prev()` select the first row shown, as an arrow does. `select` past either
  end selects that end. On an empty list every one does nothing. They apply
  on the render thread a tick after the handler, once that tick's diff is
  applied, in the order they were asked, each from where the last left the
  selection, so repeats queued while logic was busy all count and
  `query = q; results.select(2)` ends on row 2 of the rows mounted by then.
  On an element `strand check` can see is not a `list` (an `id:` written on
  it, or a component call whose root it is), they are the error
  `check::not_a_list`; reached through `self` or a conditional id they do
  nothing, and the first such call in a run says so to `strand watch`.
  `results.selected_index` (`int?`) is the selected row's place among all the
  rows, null with none and on other elements: reactive, it follows a tick
  behind the keys, and an `on change` of it is input, as of `selected`. A
  start the list takes from its `selected_index:` (below) it reads in the
  tick that sets it instead, all but the one a `nav:` list takes as its
  surface gets the keyboard again, which it reads a tick behind, as the
  keys.
- **Where a `list`'s selection starts, and where it goes.** `selected_index:
  n` on a `list` (`int?`) is the row its selection starts on, in place of the
  first: a `nav:` list selects it wherever it would select its first row (it
  mounts or comes back, its rows arrive, its input's text changes, its
  surface opens again, its rows change under the same text while the user
  has not moved the selection), and any list selects it when it mounts and
  again whenever the value changes, while the user has not moved the
  selection since (an arrow, a click, or a list action from a handler); a
  new text in its `nav:` input lets it follow again. Below 0 is the first
  row. A row the list does not have yet is waited for, never put on the last
  row: nothing is selected, `selected_index` reads `n`, and the row is
  selected (and scrolled into view) when it arrives, so a page whose rows
  and start come in after it opens lands on its row with no handler and
  never shows its first row on the way. An arrow meanwhile moves from `n`'s
  place among the rows there; Return goes where `select(n)` would, the last
  row, and activates it, and with no rows at all does nothing. Null starts
  as a list without it does: a `nav:` list on its first row, another with
  no selection, and a turn to null leaves the selection where it is. When
  the selected row leaves (logic removes it: a keyed item gone, not the
  window scrolling past it) while other rows that were there stay, the
  selection stays at its place: on the row that takes it (`selected_index`
  unchanged), or the new last row when it was the last. When no row stays
  (every row replaced, a page of the list changed, or none left) the list
  starts again: on its start, else as above. So does a list whose
  selection was on its way to a row not mounted (moved past a virtualised
  list's window, or left out of it by a scroll) when no row from before
  stays; while one does, it stays on its way. A list started again, as one
  opening again or given a new text, follows its start again, whatever the
  user moved on the rows before, and with a null start follows one that
  comes later; a Return pressed on a selection still on its way is dropped
  with the rows it was for, and activates nothing. The place a selected
  row leaves is not scrolled to, except that a `nav:` list the user has
  not moved shows its first row as it always does. (decisions.md
  list-selection) `results.selected_index` reads a start in the tick that
  sets it, not a tick behind as it reads the keys: when the list mounts with
  one, when its value changes while the user has not moved the selection,
  and when it starts again on a new text in its `nav:` input or its rows
  replaced whole, the start is what it reads, and what its `on change`
  hears once, in that tick, so a preview or highlight read from it shows
  the start's row from the first frame, never the row selected before. A
  changed start the user has not moved away from is read before anything
  that reads it runs, so an `on change` of a value read from it hears only
  the start's; one the list mounts with or starts again on is read at the
  tick's end, where such an `on change` may also hear the row before
  (never drawn), and an `on change` mounted with the list hears the start
  rather than taking it for its first value. A
  `nav:` list whose surface opens again starts on its start as the
  keyboard enters it, and logic reads that a tick after, as it reads the
  keys. (decisions.md list-start)
- **`wrap: true` on a `list`** takes the arrows and `next()` and `prev()`
  round from one end to the other; Page keys, Home and End, and `select`
  stop at the ends.
- **`axis: horizontal` on a `list`** lays its rows in a line, scrolled,
  virtualised and kept in view along x, with a plain wheel going sideways. It
  is as tall as its tallest row laid out unless something else sizes it, and
  a row with no height of its own fills it. Left and Right move the selection,
  and Up and Down don't. In an `input` with `nav:` to one, Left and Right stay
  the caret's, since that is what a text field's arrows are for; a config that
  wants them claims them (`on key "right" { results.next() }`). A row's popup
  opens with Down, and Up closes one opened from another, in place of a
  vertical list's Right and Left. `axis: both` is the error `check::list_axis`.
- **`columns: n` on a `list`** is a grid in one list, with one selection. A
  cell is a share of the list's width, `gap` between, on whole pixels; a line
  is as tall as its tallest cell, and a cell with no height of its own fills
  it. Up and Down move a line in the same column, and Down from above an empty
  cell of a short last line goes to the last row. Left and Right move one and
  stop at a line's end. Page keys move a view of lines, Home and End go to the
  ends, and `next()` and `prev()` move one across lines. With `wrap: true` Up
  and Down off an end go to that column at the other (the last row, if that
  cell is empty), and Left and Right carry on to the next line and round. It
  virtualises and scrolls by the line. In an `input` with `nav:` to one, Up and
  Down move it and Left and Right stay the caret's. Its keys are all taken, so
  a row's popup opens by no key of the list's. `axis:` beside it is
  `check::list_axis` unless written `vertical`. `grid` stays a layout element.
- **Dead keys and Compose.** A focused `input` types what the keyboard
  composes, on layouts such as `de`, `fr` and `us(intl)`, from xkb's compose
  table for the locale (`LC_ALL`, `LC_CTYPE`, `LANG`, else `C`; `XCOMPOSEFILE`
  and `~/.XCompose` as xkb reads them). No table is no error: keys type what
  they type. A key inside a sequence has an empty `k.text` and types nothing;
  the key that ends it has the composed text; a key that cancels it has an
  empty `k.text`, as xkb's state says, and the key after it is itself again.
  `k.name` is always the real key (`dead_acute`, `Multi_key`, `e`), so claims
  match as ever. Escape, the keyboard leaving, keys going to another surface,
  the focused surface closing and a pointer press end a sequence; moving focus
  by Tab cancels one as any other key does. An Escape that ends a sequence is
  spent: no handler, claim or default hears its press or release, so it doesn't
  also close a launcher. With no sequence under way Escape is an ordinary key.
  A press with Ctrl, Alt or Super held is no key of a sequence and ends one, with
  its ordinary text; AltGr types, and composes. A held key repeats what its press typed, composed or
  nothing, and is no further key of a sequence. A `type: password` input
  composes as any other. An input method (`text-input-v3`) is not supported.
- **Copy and paste.** A focused `input` copies its selection with
  Ctrl+C or Ctrl+Insert, cuts it with Ctrl+X or Shift+Delete and pastes
  at the caret, over the selection, with Ctrl+V or Shift+Insert
  (Ctrl+Shift+C, X and V too), through the compositor's clipboard
  (`wl_data_device`), on every compositor and whether or not the
  `clipboard` service runs; `on key(k)` still hears the keys. With a
  non-Latin layout active the keys match as the first Latin layout has
  them (Ctrl+V with `us,ru` and `ru` active pastes), as in GTK and Qt;
  `k.name` stays the active layout's. A
  `type: password` input copies and cuts nothing. An `input` on the lock
  neither copies nor pastes, nor does any while the session is locked:
  someone at the locked machine must not read its clipboard or plant
  one. A paste becomes one
  line (line breaks and tabs become spaces, other control characters
  go); one over 1 MiB, or not delivered within 5 s, is dropped with a
  warning. The `clipboard` service follows the selection, copies a value
  from a handler (`clipboard.copy(ip)`) and keeps a history of what was
  copied; the selection it finds when it starts (Strand starting, or a
  reconnect) is shown in `clipboard.text` but is no copy and is never
  recorded, so an entry removed or cleared stays gone (decisions.md
  m6-service-gaps).
- **The caret.** A focused `input` draws its caret where the next key
  types, a selection's moving end included: an `$accent` bar 1.5 px wide
  and as tall as its line. It blinks as a desktop's text field does, with
  nothing to set: shown for 600 ms, hidden for 600 ms (GTK's 1200 ms
  cycle), shown again at once and blinking anew from each key, caret
  move, click, change of its text and focus gained, and shown for good
  once 10 s pass without one (at the end of that cycle, 10.8 s), so a
  field left focused does not keep the shell awake. The render thread
  alone redraws it, the caret's pixels and no more; logic hears nothing
  of it. It does not blink with the desktop's reduced-motion setting on,
  in a frame at time zero (offline pictures), in the evaluation sandbox
  or on a mock desktop (`STRAND_MOCK`, the tests' screenshots), which
  hold it steady (decisions.md caret).
- **`tooltip: expr`** shows a tooltip on hover.
- **Drag and drop.** `drag: value` on a source; `on drop(v: T, at: int)`
  on a target. `at` is where it lands among the target's rows (for a
  target that is itself a row, among its siblings), counted without the
  dragged item: in its own list, without its own row (an equal item
  beside it is another row); in another list, without that list's first
  copy of it (the same value drawn by another monitor's surface). A
  row of an outer list that holds the item's list (a kanban column
  holding the dragged card) is counted. So `list.move(key, at)`, which
  moves the first item with that key, puts it where it was let go,
  in a windowed `list` too, whose rows not mounted count as well: a
  row not mounted is a copy when the `drag:` values it would hold
  mounted (its own, not those of a `list` or `for` inside it, such as a
  dock item's window dots) include the dragged item, whatever its
  `drag:` is of its item (decisions.md m5-fixups, m6-edges,
  m6-integration-w1). Values from other programs (files, apps, text)
  arrive as typed `Drop` values.
- **`pages`** shows one `page` at a time, with directional transitions;
  hidden pages unmount, so their service subscriptions stop.

## 7. Types and expressions

### 7.1 Types and literals

| Type | Literals and notes |
| --- | --- |
| `int`, `float` | `36`, `0.72`. An `int` widens to `float`. |
| `length` | `4px`, `40%` (of the container), `4ch`; a bare number is px |
| `angle` | `270deg` |
| `duration` | `6s`, `1.2s`, `200ms`, `5min`, `3h` |
| `color` | `#7aa2f7`, `#fff`, `#00000080` (3, 4, 6 or 8 hex digits), token paths, colour functions |
| `text` | `"Search apps"`; any UTF-8, escapes `\" \\ \n \t \r \0 \u{…}`; no interpolation |
| `bool` | `true`, `false` |
| `[T]` | `[]`, `["a", "b"]`; lists |
| `[K: V]` | `[]`, `[1: "web", 2: "code"]`, `[low: 3s, critical: 0s]`; dictionaries, one `V` per key |
| `T?` | `T` or `null` |
| `Async<T>` | section 8.6 |
| records, enums | sections 5.4 |

- A `T?` value must be unwrapped (`?.`, `??`) before it is used where a
  `T` is expected; using it directly is a load error.
- Using an `Async<T>` where a `T` is expected is a load error, except
  for the reads through an `Async` list that section 8.6 lists.
- `xs.fuzzy(query, by)` searches any list. `by` is a pure function giving
  an item's `text`, and the result is a `[Match<T>]`: for each item that
  matches, its `item: T`, `score: float` and `ranges: [Range]`, best first,
  equal scores in the list's order. It is `apps.search`'s matcher: lower
  case matches either case, accents are ignored unless the query has them,
  and every word of the query must match; `!`, `^`, `$` and `'` are plain
  characters, not operators, so `don't` looks for those letters, there and
  in `apps.search`. A blank query gives every item in
  the list's order, with score 0 and no ranges. `ranges` count characters,
  as `marks:` does: `text m.item.name { marks: m.ranges }`. Items with a key
  keep it, so rows keep their state as the query changes. `Match<T>` can be
  written as a type, as `Async<T>` can; a config's own `type Match` takes
  the name instead.
- **Dictionaries.** `[K: V]` holds one value of type `V` for each key of
  type `K` (decisions.md dictionary).
  - A key is an `int`, a `text` (or an alias of one, such as `AppId`), a
    `path`, a `bool` or an enum. Any other key type is
    `check::dict_key`: a `float` may be a fraction and a number with a
    unit compares by unit (`2px` and `2ch` would be two keys), so the
    help says to key by a whole number (`x.round()`) or a `text`;
    records, lists and functions have no key form. A `K?` key type is
    the same error: a key is never null.
  - A value is any type but an optional one: `[K: V?]` is
    `check::dict_value`, since a missing key already reads `null`.
  - `[k: v, …]` takes its type from the type expected, its keys checked
    as `K` and values as `V`. Without one, its keys and values each
    join as a list's items do (`[1: "a"]` is an `[int: text]`), and the
    dictionary keeps that type: it does not widen as an untyped whole
    number list does (section 5.3), so writing `0.5` into `state m =
    ["a": 1]` is a type mismatch whose help declares `state m: [text:
    float] = ["a": 1]`. `[]`
    is the empty dictionary wherever one is expected, and as a branch of
    `?:` or `match` beside one; an untyped `state
    m = []` is a list, and indexing one with a `text` key is
    `check::dict_untyped`, whose help declares it: `state m: [text: V]
    = []`. The same constant key twice in a literal is
    `check::dict_duplicate`.
  - `m[k]` reads a `V?`: `null` when `k` is absent. The key is expected
    as a `K`, so a `K?` key must be unwrapped first, as a list index
    must. A miss in a chain needs `?.`: `pins["kitty"]?.at`.
  - In a handler, `m[k] = v` adds the entry or replaces its value, and
    `m[k].f = x` writes a field of a present entry: the target is a
    `V`, so `m[k] = null` is a type mismatch whose help says
    `m.remove(k)`. A compound `m[k] += 1` is `check::dict_compound`,
    since the entry may be missing: write `m[k] = (m[k] ?? 0) + 1`.
    `m[k].f = x` when `k` is absent is an error of the handler (section
    8.3), "no entry for this key", and changes nothing, as `xs[i].f =
    x` past a list's end is. A mutation through `?.` skips a null and
    writes nothing: `m[k]?.push(x)` on an absent entry never creates it,
    and `m?.clear()` or `m?.remove(k)` on a null `[K: V]?` leaves it
    null. `m = m.filter(e => …)` replaces it whole.
  - Its entries are always in key order, whatever order they were
    written in: ints by number, `text`s and paths by Unicode scalar,
    enums in their declaration order, `false` before `true`. `keys`,
    `values`, `entries` and `filter` follow that order. There is no
    insertion or recency order to keep: another order is
    `m.entries.sort_by(e => e.value)`. When a literal's computed keys
    repeat one, the later entry wins.
  - A dictionary `state` is one value. A binding that reads `m[k]`
    re-runs on any write to `m`, and stops there unless its entry's
    value changed (section 8.1), so `on change m[k]` runs only when
    that entry changes, and sees `null` once it is removed.
  - Its members are listed in docs/reference/functions.md under
    `[K: V]`: `len`, `keys` (a `[K]`), `values` (a `[V]`), `entries`,
    `filter(e => …)` (a `[K: V]`), and in a handler `remove(k)`, which
    does nothing when `k` is absent, and `clear()`. There is no `get`,
    `set` or `has`: `m[k]`, `m[k] = v` and `m[k] != null` are those.
  - `m.entries` is a `[Entry<K, V>]`, each with its `key` and `value`,
    keyed by `key`, so `for e in m.entries { … }` needs no `key` clause
    and keeps each row by its key. `for e in m` is `check::dict_for`,
    whose fix is `m.entries`. `Entry<K, V>` can be written as a type,
    as `Match<T>` can; a config's own `type Entry` takes the name
    instead.
  - Binding a prop two-way to an entry (`value: <-> m[k]`) is
    `check::dict_two_way`: bind a `state` that starts from the entry
    (`state v = m[k] ?? 0.5`, `value: <-> v`) and write the entry `on
    change v { m[k] = v }`. A service field, an action's parameter or a command's
    output cannot hold a dictionary yet (`check::dict_service`).
- A list's members (`len`, `filter`, `find`, `push`, …) are listed in
  docs/reference/functions.md under `[T]`. `xs[i]` counts from 0 and
  reads `null` past the end. `xs.index_of(test)` is the index of the
  first item `test` is true for, as an `int?` (`null` when there is
  none). It is `find`'s position, so
  `xs[(xs.index_of(x => x.active) ?? -1) + 1]` is the item after the
  active one (decisions.md m6-owner-fixes, gap 23).
- `xs.reduce(init, f)` folds a list from its first item: `f(acc, x)` is
  called for each item in order, starting from `init`, and the last
  result is its value (`init` for an empty list). Its type is `init`'s:
  `xs.reduce(0, (a, x) => a + x.n)` is an `int` when `x.n` is, and a
  `float` when `f` gives fractions (a whole-number `init` follows `f`,
  as an untyped `state` does). A running total needs no operation of its
  own: `xs.take(i).sum(x => x.w)` is the total before item `i`, as the
  best-guess monitor layout in site/how-to/monitor-profiles.md writes it
  (decisions.md monitor-layout).
- A `text`'s members (`len`, `slice`, `index_of`, `split`, …) count
  characters (Unicode scalar values), not bytes: `"héllo".len` is 5,
  `s.slice(from, to)` is the characters from `from` up to `to` (a
  negative index counts from the end, and both are clamped to the text,
  so `s.slice(-3)` is its last three), and `s.index_of(part)` is the
  index of `part`'s first occurrence, as an `int?`. `number(t)` reads a
  decimal number from a text, spaces around it allowed, and is `null`
  when the text is not one (decisions.md flex). (json-fn) `json(v)`
  writes any plain-data value as compact JSON, records by their fields
  in order, enums by name, colours as `"#rrggbb"` (`"#rrggbbaa"` when
  translucent), durations in milliseconds, a token as its current
  value (docs/reference/functions.md; decisions.md json-fn), for
  a file a tool reads or an action's one argument.
- `t.plain(m)` is the text `markup: m` shows, without its styles, and
  `t.links(m)` its links' targets in order, as written, both read by the
  one converter the renderer uses; `m` is a `Markup` and required, and
  `none` gives the text unchanged and no links (decisions.md
  doc-formats).

A bare number where a length is expected is logical pixels: `width: 90`
is `width: 90px`. Where an angle is expected it is degrees, and where a
duration is expected it is a load error (`200ms`, `1s`: durations need
units). `1min` is `60s` and `1h` is `60min`.

A whole-number literal with no unit is an `int` (an `int` widens to
`float` where one is expected); beside another operand of an arithmetic
operator it takes that operand's type, so with `n: int`, `2500 + n` and `n + 2500`
are both `int`s (and with `x: float`, `2500 + x` a `float`). A
fractional literal (`0.5`) is always a `float`. A `float` where an `int`
is expected is a load error whose help suggests rounding it (`.round()`,
`.floor()`, `.ceil()`).

### 7.2 Operators and calls

- Precedence and associativity are grammar.md's. `==` and `!=` compare
  values; `<`, `<=`, `>`, `>=` compare ordered values (numbers, lengths,
  angles, durations, percentages, dates). `&&` and `||` short-circuit.
- An ordering comparison takes two plain numbers, or two values of the
  same kind (`10px < 20px`, `1s < 500ms`), or a length, angle or
  percentage beside a plain number, which is read in the other side's
  unit (`10px < 20`, `90deg > 45`, `40% < 50`), or two lengths in
  different units (`px`, `ch`, a percentage), whose numbers are compared
  as written: a comparison resolves neither a `ch` against a font nor a
  percentage against a size, so `2ch < 10px` is true. A duration
  compares only with a duration, and other units never mix (`1s < 2`,
  `90deg < 10px`): a load error. Two `Date`s order by time, earlier
  first (`d.date < clock.today`); a date without a time of day comes
  before every time on that day.
- `==` on two dictionaries is true when they hold the same keys, each
  with an equal value; key order is fixed (section 7.1), so how they
  were written does not matter. There is no `+` on dictionaries.
- `+` on two `text`s joins them (`name + "…"`, and `s += "!"` in a
  handler); `+` between a `text` and anything else is a load error.
- `+` on two lists of one item type joins them, the left's items first
  (`xs + [x]`, and `xs += [x]` in a handler); `[]` beside a list takes
  its item type. So does a `[]` branch of `?:` or arm of `match`: it takes
  the type the other branches give, in either order and nested (`ok ? [] :
  pkgs_of(r)` and `ok ? [] : more ? [] : pkgs_of(r)` are `[Pkg]`, and
  `ok ? [] : [1: "a"]` is an `[int: text]`); when every branch is `[]`,
  nothing gives one and an untyped `let` or `state` holding it is
  `check::needs_type` (decisions.md empty-list-infer). Lists of different item types, or a list beside a
  non-list, are a load error (decisions.md flex).
- The maths functions `sin`, `cos` and `tan` take an `angle` (a bare
  number is degrees), and `atan2(y, x)` returns one. Angles follow the
  screen: `0deg` points right (+x) and angles grow clockwise, since y
  grows down, the way `rotate` turns, so `(r * cos(a), r * sin(a))` is
  the point at angle `a` on a circle of radius `r`. `atan2` returns an
  angle from -180° to 180°, so an arc drawn from a fixed angle to it
  (`c.arc(…, from: 135deg, to: atan2(dy, dx))`) turns the other way
  once the pointer passes 180°: add `360deg` to an angle below the
  start. `pi` is the constant, a plain number: the maths functions
  take degrees, so `pi` in their angle (`sin(pi / 2)`) is a warning
  whose fix is `180deg`. `sqrt` of a negative number, `ln` of zero or
  less, and any maths result that is not a finite number (`pow(0,
  -1)`) are error values (decisions.md flex). A maths function of a
  time signal (`t`, `wave(…)`) is one too, which render evaluates each
  frame as it does arithmetic on them: `x: 20 * sin(t * 90deg)` bobs.
  Any other builtin that computes with its arguments at once (`num`,
  `pct`, `join`, …) cannot take one: a load error
  (`check::time_in_logic`).
- `==` and `!=` take two numbers exactly when an ordering comparison
  would, and compare their numbers as written, read the same way as for
  order (`10px == 10`, `2ch == 2px` and `50% == 50px` are true;
  `1s == 1000ms` is true). Units that never mix are a load error here
  too (`90deg == 90px`, `1s == 1000`, `1s == 1000px`), as they are for
  order (decisions.md m5-docs3, round 3; m5-integration-w3).
- `a ?. f` is `null` when `a` is `null`, else `a.f`. `a ?? b` is `b`
  when `a` is `null`, or an `Async` that has no value: its first load
  still pending, or a failure with no earlier value kept. An `Async`
  that has a value gives that value, the kept one included while a newer
  load is pending or after a newer load failed. Its type is the inner
  type of `T?` or `Async<T>`.
- `c ? a : b` evaluates only the chosen branch.
- Calls name their arguments by position or by name
  (`month.add(months: -1)`). Builtin functions that take nullable input
  and are marked "null in, null out" (`pct`, `dur`, `num`, `bytes`,
  `number`) return `null` for a
  `null` argument; `join(sep, parts…)` joins the parts that are not
  `null`.
- A lambda `x => e` or `(a, b) => { … }` is a value; a lambda is called
  with every argument (lambda parameters have no defaults).
- `await e` is allowed only in a handler (section 8.3); elsewhere it is
  a load error.
- A value that cannot be computed (a stale read, a failed call, a
  runaway recursion) is an **error value**, which propagates through the
  expression and is shown as a runtime fault (section 12); it never
  crashes the shell.

### 7.3 match

- `match value { pattern => result, … }` selects the first arm whose
  pattern matches. A pattern is a variant, a literal or `_`
  (any value).
- A `match` must be exhaustive: an enum match must cover every variant,
  a `bool` match both `true` and `false`, or either may end with `_`;
  any other match must end with `_`. A non-exhaustive
  match is a load error, and so is an arm that can never be reached.

## 8. Reactivity

### 8.1 Three kinds of value

- **`state`** is writable (section 5.3). **`let`s and props** are lazy
  derived values: they are recomputed only when something they read has
  changed, and only when read. **Service fields** are live values,
  writable only where the service marks them `rw`.
- A program is one reactive graph. Each binding records exactly what it
  read; when a written value equals the old one, nothing downstream
  runs. When nothing is written, nothing runs and no frame is drawn.
- A service starts when the program first reads it, is shared by every
  reader, and stops 5 s after its last reader leaves or becomes
  invisible. One field is held otherwise: a program that reads
  `clipboard.history` anywhere (a closed popup, a `let` only it reads)
  holds `clipboard` and its history from its top level for as long as
  it runs, so copies made while the history is not shown are kept; a
  program that never reads it never records it, and a config's own
  `service clipboard` shadows the rule (decisions.md m6-service-gaps).
  Likewise a `graph` whose value exists at file scope (a service field,
  or an expression over service fields, file-level `let`s, `state`s
  and settings, and constants) shows the last `history` of it as soon
  as it mounts: the program keeps that value, once per expression, for
  the longest `history` any of its graphs asks, in memory only, and
  the services it reads keep running while no visible reader holds
  them. One that samples on a clock (`cpu`, `memory`, `disk`,
  `network`'s byte rates, a `from poll` service) samples then at a
  coarser period, a twentieth of that history and at least 2 s; one
  that reports its changes as they happen keeps reporting them; a
  stream run only while watched, or a value that changes only while
  shown, records nothing hidden. A graph
  of a value tied to a list item, a component's parameter or `let`, an
  element's state or the animation clock, or whose `history` is not a
  constant (a literal, or a file-level `let` of one), shows what came
  since it mounted (decisions.md history). A graph of a list keeps each
  item's history as its own series, and a graph's columns are whole
  periods of the boot clock, its `history` over its columns, each the
  value at its period's start (as kept, else as the frames that painted
  it saw it; the period kept history starts within, the value it starts
  with), so kept values fall in the same columns whenever its
  frames come, and a value no history keeps does too unless it changed
  within a frame before a column's start (decisions.md graph-follow and
  graph-flake; sections 6.6 and 14).

### 8.2 One tick, one diff

- Writes made in one tick are batched. Every binding sees a consistent
  set of values (no binding ever sees a mix of old and new values from
  one tick), and the screen receives one change set per tick.
- **State versus events.** A state value is latest-wins: several writes
  in one tick are one change. An event (`on notifications.received(n)`)
  is a lossless queue: every event is delivered, in order.

### 8.3 Handlers

- A **handler** is the body of `on`, `after` or `every`. It is a
  coroutine: it may `await`, and other handlers run while it waits.
- Statements are `let`, `if`, `match`, `for`, `play`, expressions (an
  action call such as `ws.focus()`, or of a declared action, section
  5.7) and assignments.
- **Assignment** (`=`, `+=`, `-=`, `*=`, `/=`) writes a place: a
  `state`, a field or item of one, an entry of a dictionary one (`m[k]
  = v`, with `=` alone: section 7.1), an `rw` service field (including
  one on an item of a service's keyed list), or a settings field
  (written field by field). `x op= e` is `x = x op e`. Assigning to a `let`, a
  prop (directly or through an `id`), a parameter or a read-only service
  field is a load error with a fix. Assignment is a statement, never an
  expression.
- A handler's errors are values: a failing action or expression never
  stops other handlers or the shell. A failed `await` (an action that
  exits non-zero or prints what does not read as its `T`), or any other
  error in a handler's body, ends that run of the handler only: it is
  logged and told to `strand watch` as a fault that froze nothing, and
  every handler, that one included, runs at its next event (section 12;
  decisions.md handler-fault). A handler that fails the same way again
  (an `every` timer on each tick) is not reported again until a run of
  it completes (decisions.md handler-fault-repeat); a `strand watch`
  started since hears it at its next failing run (decisions.md
  handler-fault-repeat-watch), and so does each lock session that
  begins, since the lock's built-in password field is shown for a fault
  reported while it is up (decisions.md lock-fault-epoch).
- When a handler's node unmounts, the handler is cancelled at its next
  `await`. A reload that changes a handler's code, or anything it calls,
  restarts it and cancels and reports an in-flight `await`
  (section 10.1).

### 8.4 Events and timers

- `on name { … }` and `on name(params) { … }` run on an event of the
  enclosing node (`click`, `secondary`, `scroll(dy)`, `activate`,
  `drop(v, at)`, a surface's `show`, a popup's `dismiss`), or of a
  service (`on notifications.received(n)`). Which events exist, and
  their parameters, are schema entries. A node's event needs a node: its
  handler directly in an `if`, `for` or `match` body is a load error
  (put it on an element there, or use `when`).
- **`on change a, b { … }`** runs when any watched value changes. It
  **never** runs for the first value (at boot or mount), for a value a
  reload writes (section 10.3), or when a watched service path switches
  to another object (`audio.sink.volume` when the default sink changes):
  the new object's value becomes the baseline. A watched key, or a
  field holding it, is the exception: `audio.sink.id`,
  `clipboard.history.first?.id` or a `Hit`'s `app` (`key app.id`)
  changes with every such switch, so it runs then. Each watched value
  is judged by its own object: `on change audio.sink.volume,
  audio.sink.muted` does not run on a sink switch, but
  `on change clipboard.history.first?.id, clipboard.history.first?.text`
  runs on a new copy, and `on change audio.sink.volume, x` runs when `x`
  changes in the same tick as a sink switch. The watched expressions
  must be reactive (state, settings, services, or `let`s that read
  them). (service-ready) A handler that should also act on a service's
  first answer, or again after a failed run is replaced, names the
  service's `ready` (section 5.6): it is false until the values are in
  and turns true one flush later, as a change, so `on change
  outputs.all, outputs.ready after 1500ms { if outputs.ready { … } }`
  reconciles the starting state, every change, and each restart.
  `ready` means *reported*, not *settled* (docks enumerate late,
  daemons restore volumes after login), so a reconciling handler
  debounces. It turns false at once when the run ends or, for
  `outputs` and a declared `from dbus` service, its source goes (a
  builtin D-Bus service whose daemon goes stays ready, section 12); a
  handler that names both a list and `ready` does not run for a
  list a failing service clears, since that is a boot value again,
  while one that names only `ready` does. Other idioms: a one-shot once
  the answer is real, `after 0s while battery.ready { … }`, and a
  placeholder, `if !workspaces.ready { Skeleton } else { Strip }`. In a
  closed `bar`, `panel`, `osd` or `window` it waits, and
  when the surface opens runs once for what it missed and for a change
  made in the tick that opens it (section 5.1, which also says where
  the first opening is not seen, and how a `popup` and the `lock`
  differ).
- **`on change a after T { … }`** debounces: it runs once, `T` after
  the last change.
- **`after T while c { … }`** is one-shot: it runs at most once per
  mount of the node or component it is written in (once for the program
  at the top level), after `c` has held for a total of `T`. It counts
  only time during which `c` holds and schedules nothing while `c` is
  false; when `c` turns false the count pauses and is not reset, and
  once the body has run the timer is done, so `c` turning false and
  true again never re-arms it. A delay that runs each time a condition
  ends (a hover popup closing 200 ms after the pointer leaves) is
  `on change c after T { if !c { … } }`. **`every T while c { … }`**
  runs every `T` while `c` holds. Without `while`, the condition is
  always true.
  `every` keeps its phase: host latency does not accumulate. After a
  gap longer than its period it runs once and re-phases, so its next
  run is one period after that one; it never replays missed runs. A
  zero `every` period is an error value naming the timer, reported as a
  runtime fault (section 12), not a silent pause.

### 8.5 Two-way binding

- `prop: <-> target` binds a widget's prop to a writable place: a
  `state`, an `rw` service field, or a settings field. The prop shows
  the target, and when the widget changes the value (a slider dragged, a
  popup dismissed, text typed) it writes the target. An entry of a
  dictionary is not such a place, since it may be missing
  (`check::dict_two_way`, section 7.1).
- The prop must be one the schema marks two-way (`value`, `text`,
  `open`, …), and the target must be writable; otherwise it is a load
  error. `<->` takes one expression, a place.
- Writes through `<->` are not counted by the feedback throttle
  (section 8.7).
- A widget with a `range` shows and writes its target in that range's
  units: with `state percent = 50`, `slider { value: <-> percent;
  range: 0, 100 }` writes 0 to 100 (decisions.md graph-follow; section
  14).

### 8.6 Async values

- Some calls return `Async<T>` (`apps.search(q)`, `material(image: …)`,
  and a declared action with a result, section 5.7).
  An `Async` keeps its previous value while a new one loads, and exposes
  `.pending` (a load is in flight) and `.error` (the last load failed).
- `.value` (`T?`) is the value it holds, `null` before the first load
  finishes or after a failure with nothing kept; `.error` is `text?`.
- `x ?? fallback` gives the value it holds, and `fallback` only while it
  has none (section 7.2): a search keeps its last results while the next
  one loads, a theme its last palette while a wallpaper is quantised.
- Using an `Async<T>` where `T` is expected is a load error, so the
  loading state cannot be forgotten. An `Async<[T]>` list is read
  through in two ways, and only these:
  - `.len` and `for x in a` read its last list (empty before the first
    load).
  - `filter`, `map`, `sort_by`, `fuzzy`, `take`, `skip` and `reverse` on
    it give an `Async<[U]>` that keeps its `.pending` and `.error`; a plain list
    still needs `??` (`hits.take(3) ?? []`).
  - Any other read of it is a load error: element reads (`.first`,
    `.last`), other list methods (`join`, `find`, `contains`, …) and an
    `Async` passed where any value is accepted (`join(", ", hits)`).
- When what an `Async` binding reads changes, the new load supersedes
  the one in flight. A load a handler starts outlives the handler.

### 8.7 Feedback loops

- A **static cycle** (a `let`, token or component that depends on
  itself) is a load error naming the path.
- **Echoes.** A write to a service carries a generation tag; a service
  reporting back the value of a write still pending is ignored.
- **Runaway writers.** More than 30 writes per second to one cell from
  one writer warns (naming the handler) and throttles that writer's
  writes to 30 per second, without losing the last value: in between,
  only the latest value is held, and a compound assignment starts from
  the held value. A writer is a handler, or one run of an input
  handler (below).
- **What is not counted.** Writes from `strand set` and the other
  command-line writes, values a service reports, writes through
  `<->`, and a list's `selected_index` reading its start (section 6.7),
  which the router takes as the user's place, are never counted. An
  input handler (`on click`, `on scroll(dy)`, and the other events of a
  node the user acts on)
  is not counted until its first `await` that suspends; after it, the
  run's writes count against that run alone, not against the handler.
  So `on scroll(dy) { await x; v -= dy * 0.05 }` at 60 Hz, sixty runs
  that each write once, is never throttled, while one run that keeps
  writing more than 30 times a second is. An `on change` whose every
  target is a node's input state (`hover`, `pressed`, `focused`,
  `selected`, `pointer`, of `self` or a named node) is an input handler
  too: a drag following `self.pointer` at 60 Hz is the user. (proc-lines)
  A handler of a command's `line` event (a `from listen` service's or an
  action's) is an input handler too: a command's lines are external
  input, bounded by the command itself (section 5.6). Several runs each below the
  limit are not added up. A handler started by a service event or a timer is
  one writer however many runs it has.
- **Keyed collections.** A throttled writer to a keyed collection
  keeps a held copy of its changes, which lands as one keyed diff when
  its window has room, so items keep their identity; a write that goes
  through in between is merged under it by key, and a change that no
  longer applies is skipped and reported.

### 8.8 Who wins

- `strand set` on a `state` or a **settings field** is an ordinary
  write, the same as a handler's: a settings field's is saved to its
  file (section 11), which stays the one place its value is kept.
- For **tokens** the order is: runtime overlay (`strand set '$accent'`)
  > file > default. For **settings fields** it is: overlay > file >
  default, the overlay holding only the writes a read-only file could
  not take (section 11). When a save changes a value that an overlay
  shadows, the reload overlay says so:
  `accent: file changed but runtime overlay wins [clear]`. `[clear]`, or
  `strand clear`, removes the overlay (section 13).

## 9. Styling, tokens and theming

### 9.1 Three tiers

| Tier | What it holds | Example |
| --- | --- | --- |
| Palette | A typed schema of colour roles: Material 3's system roles one to one, plus 13 hue roles; its source's own colours and its identity ride along | `$surface`, `$fg`, `$accent`, `$on_accent`, `$error`, `$outline`, `$green`, `$bright_blue`; `$palette.mauve`, `$palette.name` |
| Base tokens | Scales and derived roles, written as expressions over the palette | `$space.2`, `$radius.lg`, `$font.ui`, `$motion.spatial`, `$surface.hi` |
| Component tokens | Knobs a component exposes for overriding | `component Toast(n) tokens { radius: $radius.lg }` exposes `$Toast.radius`; a `Toast` declared in two files (section 4.2) keeps its own `$Toast.radius` inside its file and is `$file.Toast.radius` where the bare path is ambiguous |

- Tokens are live values in the reactive graph, never constants fixed at
  load. A token change re-evaluates what reads it; nothing is rebuilt.

### 9.2 Token paths and methods

- `$name.seg.seg` reads a token. Segments are identifiers or integers
  (`$space.2`).
- A segment followed directly by `(` is a **method** on the token before
  it: `alpha`, `mix`, `lighten`, `darken` (`$surface.alpha(0.72)`,
  `$surface.mix($fg, 8%)`). Adding methods later never breaks a token
  name.
- **Template-only methods.** In a template hole and in a `file`'s
  `text:` that reads only the theme (the template scope, sections 9.7
  and 9.8) a token path also has
  `.light()` and `.dark()` (the token's value in that mode),
  `.red()`, `.green()` and `.blue()` (integers 0–255 after gamut
  mapping) and `.opacity()` (0–1). They compose (`$accent.light().red()`).
  In any other expression they are a load error (in a `text:` that also
  reads the scope, `.light()` and `.dark()` are `file::other_mode`).
  `$accent.red` is a token path and `$accent.red()` the channel, so no
  token name can hide a method. The format functions `hex` and `argb`
  (section 9.8) are ordinary functions, usable in any expression.
- `oklch(from $c, l: l + 0.12)` derives a colour from `$c`'s channels
  (`l`, `c`, `h`, `alpha`).
- An unknown token is a load error with a did-you-mean.

### 9.3 Derived tokens, overrides and lint

- **Derived tokens stay derived.** `fg.muted: $fg.alpha(0.65)`
  re-evaluates whenever `$fg` changes, including every frame of a
  palette animation. Derived tokens form a graph; a cycle is a load
  error. Colour results are gamut-mapped.
- **`tokens name { … }`** declares a token set; **`extends base`**
  starts it from another set. **Redefining a token needs `override`**
  (`override space { 1: 2px }`), a component token included; a
  misspelt `override` or a misspelt token name is an unknown-name error,
  never a new token.
- **Palette roots are reserved.** Every palette role is a token root: the
  Material 3 roles and the 13 hue roles `red`, `orange`, `yellow`,
  `green`, `cyan`, `blue`, `magenta`, `bright_red`, `bright_yellow`,
  `bright_green`, `bright_cyan`, `bright_blue`, `bright_magenta`. A
  token set that defines one without `override` is a load error
  (palette roles come from `use palette`). The first segment `palette`
  is reserved for the palette's extras and identity (section 9.5);
  declaring a token under it is a load error.
- **`use tokens expr, palette expr`** chooses the active token set and
  palette. Both are expressions, so the choice is live
  (`use tokens prefs.compact ? compact : base, palette scheme`).
- **Lint.** A raw hex colour in a prop, or in a declaration that hands
  it on as a colour (`let`, `state`, a `fn`'s result, a parameter
  default), is a warning (use a token). Defaults in settings files and
  `material(seed:)` and `palette(…)` arguments are exempt.

### 9.4 Subtree overrides: set

- `set { $token: expr; … }` as a tree item overrides tokens for the
  enclosing node and its descendants. On the right-hand side a token
  names the **inherited** value, so `set { $surface: $surface.alpha(0.5)
  }` is not a cycle. Derived tokens re-derive inside the subtree, and a
  `set` override beats a component token's default.

### 9.5 Palettes, importers and the built-in theme

- A program with no `tokens` or `use` is themed by the **built-in
  theme**: design.md's base tokens (`space`, `radius`, `font`, `motion`,
  `elevation` and the derived roles `surface.hi`, `fg.muted`,
  `fg.faint`, `accent.hover`, `accent.container`, `border`), and the
  palette `material(seed: system.accent ?? #7aa2f7, dark: system.dark,
  contrast: system.contrast)`. A token set that defines only some base
  tokens takes the rest from the built-in theme.
- Palettes come from `material(seed: …)`, `material(image: …)` (an
  `Async`: the image is quantised off the logic thread and cached by
  content), or `import("…")` (Material seed or image, base16/base24,
  Catppuccin, matugen output, W3C design-token JSON). Every importer
  fills the whole palette schema; one table derives any role a source
  lacks.
- `palette(from:, dark:, <role>: …)` builds a palette from colours of any
  source. A role left out or null comes from `from`; without `from` the
  table derives it, and with no colour at all the result is null. A given
  role re-derives what the table derives from it. Its roles are the palette
  schema's, so an unknown name is a check error; a token as a colour is a
  runtime error. A change in its colours is a swap as any other.
- **Hue roles** are palette roles for what has to stay recognisably
  coloured (terminal colours, success and warning). A source with hues
  fills them as given and they are never altered: base16 `08`–`0E`
  (red, orange, yellow, green, cyan, blue, magenta), base24 `12`–`17`
  (the six brights), Catppuccin's red, peach, yellow, green, teal, blue
  and pink. A missing hue is the canonical hue harmonised toward the
  accent (at most 15°), at Material tone 80 in dark and 40 in light (the
  canonical hues are the sRGB primaries and secondaries, with orange
  `#ff8000` between red and yellow); a
  missing bright is its base hue with OKLCH lightness +0.08 in dark and
  −0.08 in light. Hue roles are fills, never text/background pairs, so
  the contrast guard does not touch them. A persisted palette written
  before the hue roles derives them as it derives any missing role.
- **Extras and identity.** An importer also keeps every colour of its
  source, in source order, as `$palette.<name>`: the source's name in
  snake_case (lower-cased, any other character `_`, a group path's dots
  kept as segments), so base16's `base0D` is `$palette.base0d`,
  Catppuccin's `mauve` is `$palette.mauve` and a W3C
  `color.brand-primary` is `$palette.color.brand_primary`. The palette's
  identity is read-only: `$palette.name` (the scheme's own name, else
  the source string), `$palette.source` and `$palette.dark`. A source
  colour or W3C group named `name`, `source` or `dark` is kept as
  `name_`, `source_` or `dark_` (a group `dark` holding `surface` is
  `$palette.dark_.surface`, since `$palette.dark` is the identity's
  bool); a later segment is never renamed. Two source colours that come
  to the same name are an import error naming both. A role's own colour
  is kept as an extra too (matugen's `primary` is both `$accent` and
  `$palette.primary`). `material()` and the built-in palette keep one
  extra, `source_color`, the seed. Extras and identity are read in
  the template scope (section 9.8) and (M6) anywhere else an
  expression reads tokens: a prop, a binding, a handler. There an extra
  is a `color` (which extras a palette has is known only when it is
  made), `$palette.name` and `$palette.source` are `text` and
  `$palette.dark` a `bool`; an extra is read as a token, so a swap
  springs it as it springs a role. A missing extra without `??` is an
  error where it is read (in a prop, a runtime error naming it; the
  prop keeps its last value), and `$palette.<name> ?? fallback` gives
  the fallback. A token's own value and a `use` clause make the palette
  and cannot read it (a load error).
- `system.dark`, `system.accent` and `system.contrast` follow the
  desktop's portal settings live.
- The last palette is persisted, so boot never shows default colours
  first; the old palette holds until a new one is ready.

### 9.6 How a swap animates

Writing the value a theme reads, a portal change, a new wallpaper,
`strand set` and saving a theme file all take the same path:

1. Dependent tokens re-resolve.
2. Only the palette roots spring, in OKLab; every derived token is
   re-evaluated from them each frame, so it stays exact mid-animation.
3. **Contrast guard.** Text lightness is solved to keep the declared
   text/background pairs at 3:1 or better throughout. Where a light↔dark
   swap makes that impossible, the surface snapshots its old frame once
   and crossfades.
4. What cannot interpolate snaps (section 6.6).
5. `file` outputs (section 9.7) re-render from the new targets after
   the tick's diff is sent; they never see a spring's in-between
   values.

### 9.7 The file element

`file "<path>" { template: "<template path>"; run: [<argv>] }`, or
`text: <expr>` in place of `template:`, keeps a file outside the config
in step with the theme, and (live-files) with anything else the config
reads: another program's config from a settings slider, a status file
from a service, a compositor fragment from `outputs.all`.

- **Placement.** It is an element in the one call shape, so it may
  appear in any tree, where `if`, `match` and `for` gate it and `when`
  can change its props (never switching it between `template:` and
  `text:`: a `when` holds props only). It draws nothing, so it may also stand at the
  top level of a file (grammar.md `top_file`); every other element and
  every prop at the top level stays a load error (section 4.1).
- **Props.** Exactly one of `template:` (a path relative to the config
  directory) and `text:` is given; both or neither is a load error. The
  positional path, `template:`, `text:`, `run:` and any `when` condition
  are ordinary expressions in the enclosing scope (`state`s, settings
  fields, `let`s, `fn`s, services and loop variables), so a `for` can
  mount distinct paths.
- **`text:`.** A `text:` that reads only the theme (the template scope,
  section 9.8: tokens, `??`, `join`, `hex`, `argb`) is one template
  hole, and has the template-only methods (`$surface.light()`). One that
  reads anything else is an ordinary expression whose value is written
  by 9.8's Values rule: text as is, a number in shortest form, a bool, a
  colour as `hex(c)`, a token's current value (inside `join` too, as a
  template's `join` writes it); a list or record is an
  error naming its type. One that reads a token on its way (`join`,
  `hex`, a `let` that reads one) waits for the palette as a template
  does, so it is never written from the fallback palette first. `.light()` and `.dark()` in such a text are an
  error (`file::other_mode`): the other mode needs a text that reads
  only the theme, or a template file. A `text:` that is `null` writes
  nothing and runs nothing: the file is left as it is, and bytes not yet
  written there are let go, as when a render fails.
  `text: wm.name == "Hyprland" ? monitors() : null` is how a
  top-level `file` (which no `if` can gate) says "leave it".
- **Pending.** Nothing is written, and `run:` does not run, while a
  service the `file` reads (in its path, `text:`, `run:` or a `when`,
  through `let`s and `fn`s) has `ready` false (section 5.6): its values
  are defaults, so a `??` fallback is not written either. It is written
  once every one has answered. A write from before it turned false, still
  waiting for its turn (the 500 ms pacing below), lands: it was made from
  values that held. A service with no run up (failed, backing
  off) makes it a standing notice naming that service, kept while it
  waits (that earlier write landing does not take it away); one starting is
  no news, and one that is up but has not answered within 10 s (a
  declared `from dbus` service whose daemon is absent, a poll that has
  not succeeded) is a standing notice naming it, given once per wait. A
  builtin whose backend is absent (`battery` without UPower) is ready
  with its defaults, and is written. A top-level `file` holds the services it reads. The positional path resolves as
  a settings file's does (section 11): `~/…` from `$HOME`, an absolute
  path as given, anything else against the config directory, never the
  working directory of `strand run`. One path mounted from two places
  (a `file` in a `bar` on every monitor) is an error naming both.
- **`run`** names a command run after the file is written; its program
  needs `permit exec` (section 5.6), else it is a load error. `strand
  check` checks literal template paths, the one-of rule and `run`
  against `permit exec`.
- **When it is written.** The content is re-rendered when what it reads
  changes: dark/light, `use palette`, token and settings edits, a
  wallpaper once its `Async` palette resolves, `strand set` and `strand
  clear` overlays, and edits to the template file, which is watched. The
  file is written only when the rendered bytes differ from what Strand
  last wrote, and at boot when they differ from the file on disk. A
  path is written at most once per 500 ms: the first write lands at
  once, and the newest content of the window when it ends (a status
  file following a playing track writes twice a second at most; a
  longer pace is `on change x after 2s { snap = x }` and a text reading
  `snap`). The
  write is atomic, follows symlinks and keeps the file's mode; any error
  writes nothing and is reported with its location, and the last good
  file stays. A refused or failed write is tried again after 1 s,
  doubling to 10 s, until it lands or newer content replaces it, with
  one notice per reason.
- **`run`** follows 200 ms after that file's last write, at most one
  run per file with one re-run queued, and is killed with its process
  group after 10 s. A `run:` that changes what its file is written from
  (a compositor reload that changes `outputs.all`, which the text maps)
  is held: when a write comes while the file's `run:` runs or within 1 s
  of it ending, three times in a row, the `run:` is held, with a
  standing notice, until the file is quiet for 1 s; it then runs once
  for the last content, and a fourth round right after that run holds
  it again without one. The next write that no run caused runs it as
  usual. A write while held that comes more than 1 s after the last run
  ended shows the text changes on its own (a player's position, once a
  second): the hold goes at once, and its writes are no rounds until
  the file is quiet for 2 s. While held, the notice stands: a held
  write does not take it away. A failure is a notice and a `strand watch` event,
  saying why as section 5.8 does, and the last good file stays. A file's standing notice (an unowned
  target, a failing `run`) lasts until its next write lands, and a
  `strand watch` started later hears it.
- **Ownership.** Strand never overwrites a file it did not write: an
  unowned target is a notice offering `[replace]`, and a `.strand`
  target is refused. Both are judged on the file actually written, links
  followed: a link to a missing file is refused rather than replaced,
  and a link to a `.strand` file is refused like one. Removing a `file`,
  changing its path or its render failing stops its updates (the
  retries of bytes not yet written); a `run` due for a write that landed
  still runs. Removing a `file` never deletes the file.
- **Code files.** A generated file a program runs (a compositor's Lua
  or KDL, a shell script) runs at that program's next reload, outside
  `permit exec`. Text from outside (an output's `make`, a track title,
  an SSID) belongs in selectors and keys; anywhere else, escape it for
  the target's syntax with a `fn` (`fn lua(s: text) -> text { "\"" +
  s.replace("\\", "\\\\").replace("\"", "\\\"") + "\"" }`). A
  password reaching `text:` is `check::secret_flow`'s warning, as for
  `run:` (section 5.1).

### 9.8 Templates

A template (a `template:` file, or `strand export --template`) is text
of any format with holes. A `file`'s `text:` that reads only the theme
is one hole in the same scope; one that reads more follows section 9.7.

- A hole is `{{ expr }}`: one expression, ending at the first `}}`
  outside a string literal. A literal `{{` is written `{{ "{{" }}`.
- **The template scope** is tokens and their methods (the template-only
  ones of section 9.2 included), the palette's extras and identity
  (section 9.5), literals, `??`, `join` (which skips `null` parts
  only: an absent extra or other mode inside it is the same error as
  outside, and `?? null` skips one), and the format functions
  `hex` and `argb`. Services, `state`, `let` and `fn` are not in scope;
  naming one is an error saying that a template reads the theme only
  (`template::not_theme`), so a template file and `strand export
  --template` depend on the token tables alone. (live-files) `hex` and
  `argb` are ordinary functions too: `hex(prefs.accent)` in a label,
  `outputs.all.map(o => …)` in a `text:` (a token they are given is
  read from the current table).
- **The other mode.** `$x.light()` and `$x.dark()` evaluate the whole
  theme again with `system.dark` negated, top-level `let`s that reach it
  included, and read that token there; runtime overlays apply to both
  modes. When the theme gives the same mode either way, reading the
  other mode is an error unless `??` replaces it
  (`{{ $surface.light() ?? $surface }}`).
- **Values.** `hex(c, alpha: false, hash: true)` writes `#rrggbb`, with
  `alpha: true` `#rrggbbaa`, with `hash: false` no `#`; a translucent
  colour given to `hex` without `alpha: true` is an error, never made
  opaque. `argb(c)` writes `0xaarrggbb`. A bare colour is `hex(c)`. Hex
  is lowercase. A number is written in shortest form with at most three
  decimals and no unit (a pixel length is its number, an angle its
  degrees, a duration its milliseconds); a length that is not pixels is
  written as Strand writes it (`40%`, `4ch`, `auto`); a string or
  keyword as is; a bool as `true` or `false`. Any other value (a font,
  a transition, a shadow list, insets, corners, a paint, a border, a
  list) is an error naming its type.
- **Errors** carry the template's file, line and column with a caret,
  all are reported, and nothing is written on any error. A re-render of
  the same inputs is byte-identical.

## 10. Identity, state and reload

Saving a file is a state change, not a restart. A reload reconciles the
new program with the running one.

### 10.1 What each edit does

| Edit | What happens | State kept? |
| --- | --- | --- |
| Token value | Token table swapped; colours spring | Yes |
| Prop or binding | Patched in place; animates from its current value | Yes |
| Node added or removed | `enter` / `exit` play; siblings glide | Yes, elsewhere |
| `state` default | Adopted only if the value was never changed | Yes, if you changed it |
| `state` name or type | That one cell resets, with a warning | No, that cell only |
| Handler code | Restarted; an in-flight `await` is cancelled and reported | Yes |
| Timer duration | Remaining time rescaled | Yes |
| Surface layer, namespace or kind | Only that surface is recreated | Yes |
| Custom service declaration | Only that service restarts; built-ins never do | Yes |
| Anything inside `lock` | Deferred until unlock | Yes |

- (removed-state-notice) A `state` is renamed when its file or
  component (in the same place of the tree) loses a cell and gains
  another in the same save; the old cell resets with a warning,
  `launcher.wide: reset (renamed)`. A file renamed in one save is one
  owner under both names, so its cells reset as renamed. A cell removed
  while its owner gains none is gone without a word, unless its whole
  file went while it held a value you set (`removed with its module`);
  when an owner loses more cells than it gains, Strand cannot tell which
  were renamed: each says `renamed or removed`. The warning, like every row the reload overlay lists for a
  reload, is one of the `reload` event's `notices` in `strand watch`;
  the cell is also under its `reset`.
- (dictionary) A dictionary keeps its entries through a reload by key:
  an enum key follows its variant by name, so reordering the enum
  reorders the entries. A variant removed drops the entries it keyed
  and keeps the rest, and one line says so, `island.used: dropped 2
  entries (key no longer in Urgency)`; a value that no longer fits
  resets the cell, as a list's item does.
- A handler counts as changed when its code or anything it reaches
  (the `fn`s and `let`s it calls or reads) changed; an unchanged handler
  keeps its in-flight work.
- A rescaled timer keeps the fraction it has counted and finishes at the
  new duration; an `after` that already ran stays done.
- A surface's state is keyed by its place in the program, not its name,
  so a renamed surface keeps it. Turning a `bar` into a single surface
  keeps its state when it had one instance, and resets it with a warning
  when it had several.
- (window) A reload keeps an open `window` open, with what the
  compositor said of it (`w.maximized`, `w.tiled`, `w.focused`,
  `w.decorated`); its `title`, `app_id`, size limits and `decorations`
  change on the open window in place, and a new name makes it again,
  as for any surface (decisions.md window).

### 10.2 Identity

- A node keeps its identity while its source text maps to it, so editing
  a node's own props never resets it, and wrapping a node in a container
  keeps it. Next, `key` or `id` decides, then position among siblings of
  the same kind. A changed kind is a new node. Real ambiguity resets with
  a warning; Strand never guesses.
- Nodes moved into a different component (by hand, or by the LSP's
  "extract component") are new nodes: their state resets.
- State lives on components, surfaces and list items, never on leaf
  elements (section 5.3), so editing a node cannot take a popup's state
  with it.
- A `bar`'s per-monitor state is keyed by the monitor (make, model and
  description) and survives a reload, and an unplug of up to 30 s.

### 10.3 State defaults and persistence

- A state cell takes a new default only if it still holds the old one.
  Otherwise it keeps its value and the reload overlay says so:
  `launcher.query: kept "fir" (default changed) [reset]`.
- An adopted default, and any other change a reload makes to a live
  cell, is a **reload write**: `on change` takes it as its baseline and
  does not fire.
- **`persist`** stores the value with a hash of its default, under
  `persist` in the state directory (`$XDG_STATE_HOME/strand`, or
  `$STRAND_STATE_DIR`: section 13). At start, a stored value whose
  default hash matches is used; when the default changed, an unchanged
  stored value adopts the new default and a changed one is kept and
  reported once. A corrupt store gives the default and a warning.
- (dictionary) A persisted dictionary is stored as `[key, value]`
  pairs in key order, `[[3,"0x55"],[5,"0x7a"]]` (an `int` key a
  number, an enum key its variant's name), so the same entries are the
  same stored value and the same default however a literal ordered
  them. The reader also takes pairs in any order (of two with one key
  the later wins) and an object of key texts, `{"3": "0x55"}`, but a
  store is not for editing by hand: its header holds a checksum of the
  value, so a store edited by hand reads as corrupt (it is moved aside,
  and the cell gets the default and a warning). Values people edit
  belong in a settings file (section 11).
  An entry whose enum key the config no longer declares is dropped as
  the store is read, with the line a reload gives (10.1), at each start
  until the cell is next written; anything else that does not read as the type, a list of
  records turned into a dictionary among them, gives the default and a
  warning: there is no migration.
- Builtin services keep their own state beside `persist`, in the same
  directory (readable only by you): `apps`' frecency, and, while
  `notifications.remember` is on (the default), `notifications.all`,
  so the notification history comes back after a restart (without
  buttons, never as popups; a sender's `transient` notifications are
  never kept). `notifications.remember = false` erases it at once and
  stays off.

### 10.4 Escape hatches

- **`@reset`** on a `state` declaration resets that cell to its default
  (and removes its persisted value) when a reload commits it; the other
  cells are untouched. It resets the cell again on every later reload
  while the attribute stays (an edit of any file reloads the program),
  so it is meant to be removed after one save.
- **Reset subtree** (the inspector, IPC `reset{node}`) resets the state
  under one node, as `strand reload --hard` does for the whole shell.
  Settings are untouched.
- **`strand reload --hard`** drops non-persisted state and recreates
  every surface.

### 10.5 The commit

1. **Coalesce.** A reload waits 15 ms after the last completed write, so
   "save all" is one batch (50 ms when the latest event removed a
   watched file, so delete-then-create is one edit, also when a batch
   is cut while the file is missing, unless the directory is polled
   (NFS); never more than 500 ms in all).
2. **Skip no-ops.** A file whose content is unchanged stops here,
   including Strand's own writes.
3. **Check.** The changed modules are parsed and the program is
   type-checked off the rendering path; the shell keeps running.
4. **Commit atomically.** The largest changed set that type-checks with
   everything that references it is committed in one tick, with no
   blank frame; the rest is held back with its diagnostics.
5. **Keep the last good tree.** On error the running shell stays as it
   was. The last good sources are cached, so a config broken at boot
   runs its last good version.

## 11. Settings files

`state prefs from "prefs.toml" { accent: color = #7aa2f7; compact: bool =
false }` declares typed, two-way settings stored in a TOML file that
people can edit by hand.

- A relative path is resolved against the config directory; `~/…` is
  in the home directory.
- Each field is `name: type = default`. Fields are read as
  `prefs.accent`; the record itself is not assignable, only its fields.
- **Each field is checked on its own.** A bad value keeps that field's
  last good value with a diagnostic; the other fields still apply. A
  TOML syntax error keeps every last good value. A deleted key springs
  back to its default. The first write creates a file that does not
  exist yet, and its missing directories. A file that does not exist
  yet gives every field its default, and reading it creates nothing.
- Edits to the file apply live, as per-field writes.
- **A dictionary field** (`wallpapers: [text: path] = []`) is a TOML
  table: a `[wallpapers]` section or an inline `{ "DP-1" = "…" }`. Each
  key is read by the key type: an `int` in decimal, an enum's variant by
  name, `true` or `false`, a `text` or `path` as written (a dotted app id
  quoted, `"org.gnome.Nautilus" = 0.5`). One bad entry (a key that does
  not read, two keys that read as one such as `3` and `03`, or a value
  that does not fit) keeps the whole field's last good value, with a
  diagnostic naming the key: `prefs.toml: wallpapers: "DP-1": expected
  path; keeping its last good value`. A deleted table springs back to
  its default, as a deleted key does.
- (settings-tables) **A record** may be written as an inline table,
  `size = { w = 3, h = 4 }`, or as a `[size]` section, and **a list of
  records** as an array of inline tables or as TOML's array of tables,
  one `[[pins]]` section per element; so may a record wherever a type
  puts one, a dictionary's values and a record's own fields among them:
  `profiles: [text: Profile]` reads `[profiles.desk]` with its monitors
  as `[[profiles.desk.mons]]`. A field the record leaves out is its
  default. A key the record does not have is a bad value, so a typo
  does not pass for the default: `monitors.toml: profiles: "desk":
  mons[0]: unknown field "scael"; keeping its last good value`. One bad
  entry holds the whole field, so a removed record field the file still
  names (or a typo in one profile) holds every profile at its last good
  value. **A field whose value in the file is bad is not written**: a
  write of it stays live, with a notice (`monitors.toml: profiles: not
  saved while its value in the file is bad; fix it there`), since
  writing it would replace what the user wrote there, other entries of
  a dictionary among it; once the file reads again, it wins. Other
  fields are saved as usual.
- **Writes** (`<->`, handler assignments, `strand set prefs.compact
  true`) are saved after 250 ms of quiet and keep the file's comments,
  spacing and order. A dictionary is written key by key into the table
  the file has, a section or an inline one: a changed entry keeps its
  place and comment, a removed one is deleted, a new one goes at the
  table's end; a field the file does not have yet is written as its own
  `[name]` section, after the file's other keys. A record written as an
  inline table keeps the spacing of each field the same way.
  (settings-tables) A record goes back into the form the file has it
  in: a `[section]` stays a section, merged key by key, and a new record
  among records written as sections is a section shaped like them;
  (settings-shape) one among inline records is inline, and with neither
  to follow (no file yet, a new field, a dictionary's first entry) a
  record that holds records is a `[section]`, its lists of records
  `[[…]]` tables, while a record of plain values stays one inline line. A
  list, inline or `[[name]]`, is merged by value: an element that reads
  the same as one the file has keeps that one's text and the comments on
  it, in the new order; (settings-tables follow-up) so does one changed
  in a field or two, or changed in place where no other element was,
  only its changed values replaced; any other is written afresh in the
  shape of its siblings, and one no longer in the list goes with its own
  comments. Every other comment and blank line stays: the comments right
  above a table or key are its own, and what is above a blank line over
  them (a header, a commented-out block) is the file's and stays where it
  is, above what follows when the table or key under it goes.
  A value that reads the same as what the file says (`1` for `1.0`, keys
  in another order) is left as written. Writes follow
  symbolic links and replace the file through a temporary file and a
  rename. A read-only target (such as a file in `/nix/store`) gets the
  write in an overlay in the state directory instead, with a
  notice.
- Who wins between the overlay, the file and the default: section 8.8.
- A live reload keeps each field whose type is the same, carrying its
  values into the new program by name (section 10.1): an enum field or
  key follows its variant, and a dictionary's entries whose key variant
  is gone are dropped with one overlay line, as a kept `state`'s are.
  The file may still name the old variant; its next read says so and
  keeps the field's last good value.
- (check-settings; decisions.md check-settings) **`strand check` reads
  each settings file** the config declares, resolved as above and read
  through symlinks, with the shell's own decoder, and reports what the
  shell would not load, each at its line in the TOML file with the
  declaration as a second label. A file that does not exist is fine (the
  first write makes it). One that cannot be read
  (`check::settings_unreadable`) or is not TOML
  (`check::settings_syntax`) is an error: the shell takes nothing from
  it and never writes it. A field whose value does not read as its type
  (`check::settings_value`: a wrong type, a key a record does not have, a
  dictionary key that does not read) is a warning, with the message the
  shell's notice gives, as the shell keeps that field's last good value
  and loads the rest; so is a key no declaration of the file has
  (`check::settings_unknown_key`, with a did-you-mean), which the shell
  never reads. Every problem is reported, several in one field too, not
  only the first the decoder stops at. The overlay and the last-good
  snapshot are the running shell's and are not read. The language
  server reports the same, each at the declaration that reads the file,
  its message naming the TOML file and line, and reads a declared file
  again when it changes or appears.

## 12. Errors and faults

- **Load errors** (sections 2 and 10.5) never stop a running shell. A
  load error that survives 250 ms of quiet opens a dismissible overlay
  listing every diagnostic with its labels and fixes; clicking one opens
  the file in `$EDITOR`. A save fixed within those 250 ms (format on
  save, delete then create) never opens it.
- **Runtime faults** freeze only their own component, outlined in red,
  until a reload fixes it; the rest of the shell runs on. A handler's
  error (section 8.3) is a value, not such a fault: it freezes and
  outlines nothing. A fault inside the `lock` shows the built-in password field
  (section 5.1), a handler's error there included.
- **Service failures** reach the program as values (an action's error,
  an `Async`'s `.error`) and as service diagnostics; they never stop the
  shell. A diagnostic names its service (a `from poll` command that
  fails is one, said once until a poll answers); one that no longer
  holds is resolved (a poll that answers; a reload that changes or
  removes its service; a later run that stays up 30 s, for a run that
  failed), and `strand watch` tells a watcher that starts later the
  ones still open, not a one-off warning such as a copied image that
  could not be kept (decisions.md build-ready-failures). An action of a builtin service that cannot run (its daemon or
  bus missing) is never a runtime fault: it is logged and arrives as
  that service's failure event where it has one (`session.failed`,
  `network.failed`, `bluetooth.failed`, `outputs.failed`,
  `clipboard.failed`, `drives.failed`), as the daemon refusing it would; a write to such a service is dropped and
  logged, the field keeping the service's last value. Where a daemon
  may be missing, `available` says whether it answers (`network`,
  `bluetooth`, `session`, `brightness`, `drives` for UDisks2, `power`
  for power-profiles-daemon, `outputs` for the compositor's output
  configuration and `clipboard` for its data control), false too while
  a failed service waits to try again, so a config can hide what cannot
  work (decisions.md m6-owner-fixes, gaps 18 and 20; m6-service-gaps,
  gap 30; drives; power-media-kbd). Every service's `ready` (section
  5.6; one with no run is always ready) is false from the moment a run fails until a new run has
  answered; a service whose source goes while it runs (`outputs`: the
  compositor's connection or its output manager; a declared `from
  dbus` service: its daemon) turns `ready` false before it clears what
  it showed, so no reader sees the cleared values as a change
  (decisions.md service-ready). A builtin D-Bus service (`battery`,
  `network`, …) whose daemon goes stays ready and reads it again: what
  it shows then is a change.

## 13. The command line and IPC

- `strand run [dir]` runs a config; `strand check [dir | file]` checks
  it without running it; `strand fmt [--check] [paths]` formats files.
- `strand new [dir]` writes a starter shell, the guide's level-1 bar as
  `bar.strand`, into `dir` (default `$XDG_CONFIG_HOME/strand`), made if
  missing; a directory with anything in it is refused and left as it
  was. `strand compositor-rules` prints Hyprland layer rules for the
  compositor's config, to paste: one turning layer animations off for
  every `strand-` surface, and the blur rules; it never changes the
  session.
- A running shell answers commands over a Unix socket
  (`$STRAND_SOCKET`, else `$XDG_RUNTIME_DIR/strand-<display>.sock`) and
  over D-Bus:
  - `strand get path` reads an exported value, a settings field or a
    token (`$accent`); service fields are not read;
  - `strand set path value` writes an exported `state` or a field of one
    (an ordinary write), a settings field, a token (a runtime overlay;
    section 8.8), or an `rw` service field (a builtin's, a plugin's or
    the config's own `service … from`). The value is text read by
    the target's type: an enum variant by name, `true`/`false`, a number
    with its unit, `#rrggbb`, `null` for an optional. For a service
    field, a signed number or percentage (`+5%`) is a step from the
    current value, never below 0;
  - (dictionary) after a dictionary, the rest of the path is one key,
    read by the key type, so a dotted app id is one key: `strand get
    island.last_win.3` prints that entry, or `null` when it is absent,
    and `strand set prefs.scale.org.gnome.Nautilus 0.5` writes one entry,
    inserting or replacing it, its value read by the value type. `strand
    get` of a whole dictionary prints an object keyed by each key's text
    (`{"3": "0x55"}`) for `--json`, and its entries in key order as text.
    A whole dictionary is not set from text, and an entry is not removed
    (`null` is never a dictionary's value): both are refused, naming what
    does it (`strand set path.<key> value`, a handler's `m.remove(k)`). A
    key that does not read as the key type is refused, naming it;
  - `strand toggle path` flips an exported `bool` state, settings field
    or `bool` dictionary entry (an absent one becomes `true`);
  - `strand call target args…` calls a service-level action; the
    actions of the builtin services that take passwords (`auth`,
    `polkit`, `greetd`) are refused, since a password is typed into the
    shell, never sent over the socket;
  - `strand clear path` removes a runtime overlay;
  - `strand watch [--json]` streams events: reloads (files, edit class,
    kept and reset cells, timing and diagnostics), runtime faults and
    notices;
  - `strand reload [--hard]` rescans now (section 10.4);
  - `strand export json | base24 | --template <file> [--palette
    <expr>]` writes the theme to stdout, or atomically to `-o <file>`
    as a `file` element writes (through a link, the file's mode kept;
    section 9.7):
    `json` the palette's identity, its roles, every resolved token and
    its extras; `base24` a base24 scheme; `--template` a template
    (section 9.8). Without `--palette` it asks the running shell
    (overlays included), else solves the config's theme offline without
    writing anything, else fails with "no palette: run strand once, or
    fix the theme" and the cause. `--palette` is always offline: the
    base tokens and that palette, no config. A broken theme or `--palette`
    is an error, never the built-in palette. The `export` request is
    served over the socket only, not D-Bus;
  - `strand report [--json]` describes the running shell for a bug
    report: the compositor and its globals with versions, the outputs
    and their scales, the process's PSS, the GPU's status, reason and
    lost-device count, and each surface's backend, why it is promoted
    and its frame times (p50/p95/p99 over the frames drawn among its
    last 600 paints, with the drawn and unchanged counts), and (window)
    for a window what the compositor last said of it: tiled,
    maximised, fullscreen or floating, focused, who decorates it, and
    the axes the compositor sized. It carries no
    serials or ids. The `report` request is served over the socket
    only, not D-Bus. (Built, decisions.md report.) `strand report
    words… [--json]`, given words describing a glitch, saves a glitch
    report instead: a directory under `reports` in the state directory
    (the newest 20 are kept) holding those diagnostics, the words, the
    last minute or so of input and service changes the shell keeps in
    memory while `system.replay` is on (the default; never typed text,
    clipboard contents or anything while locked), every service's
    state, each surface's last frame and a copy of the config. It
    prints the directory and a line to give a coding agent, and is
    refused while the screen is locked. `strand replay [report-dir]
    [--no-open]` replays the newest report (or the one named) in the
    evaluation sandbox and opens its viewer; the sandbox is a separate
    program, `strand-eval`, run from beside `strand` or from `PATH`,
    and without it the command says so and fails. (Built, decisions.md
    replay-owner.)
- **One shell's variables.** `STRAND_SOCKET` picks the socket a shell
  answers on and the one a command reaches; `STRAND_STATE_DIR` names
  the directory a shell keeps its state in (`persist`, settings and
  token overlays, palettes, clipboard history, `file` manifests;
  default `$XDG_STATE_HOME/strand`), read by `strand run` and `strand
  export`. Each counts only when absolute. Together they run a second
  shell beside the first (`STRAND_SOCKET=… STRAND_STATE_DIR=… strand
  run dir`) without changing the session's XDG variables. They address
  that shell only: no program it starts (an app launch, a declared
  action's command, an `exec` source, a `file` element's `run:`, the
  overlay's editor) inherits them, so `strand` in a terminal it opened
  reaches the display's shell; every other variable is passed on as the
  shell got it (decisions.md launch-env).
- Paths use the program's own names: `file.name` for exports
  (`launcher.open`); `file.settings.field` for a settings field, or
  `settings.field` when exactly one file declares settings with that
  name, exported or not (`prefs.compact`); `service.field` for a service
  field (`audio.sink.volume`); `$token` for a token.
- **The D-Bus name** is `io.github.jakeb_grant.Strand`, both the bus
  name and the interface name, at object path `/`, owned when
  `strand run` starts; a second running instance runs without D-Bus IPC.
  **The name may change before 1.0** (decisions.md m5-owner, Q12).
- **Over D-Bus**, the interface's methods are the scripting commands:
  `Get(s path)`, `Set(s path, s value)`, `Toggle(s path)`, `Clear(s
  path)`, `Reset(s path)`, `Call(s target, as args)` and `Reload(b
  hard)`. Each returns the socket's answer as JSON text (`{"ok": true,
  …}`); a refusal is the error `org.freedesktop.DBus.Error.Failed` whose
  message is the socket's `error`. `Reload` returns once its load is
  committed, with its event. Watching is the signal `Changed(s event, s
  data)`: every event `strand watch --json` prints, `event` its kind
  (`reload`, `fault`, `notices`) and `data` the event as JSON.
  `export`, `report` and the inspector's commands are served over the
  socket only (decisions.md m5-ipc, m5-fixups): a D-Bus `Report` is an
  unknown method.
- A plugin binary (section 5.6) answers every command above as
  `strand` does, against its own schema, and adds `--write-schemas`.
- `strand help` lists every command and the variables above. Commands,
  their flags and their output formats are covered by the compatibility
  policy only where this section names them.

## 14. Compatibility

In 1.x:

- no syntax is removed, and no syntax changes meaning;
- builtin schema entries (elements, props, service fields, actions) are
  only added, never removed or changed in meaning.

So a program accepted in 1.x stays accepted with the same meaning; a
program rejected may become accepted when a rule is added. Diagnostic
codes and wording, performance targets, and CLI surface section 13 does
not name are outside this policy (decisions.md m5-docs).

Anything else waits for 2.0. After the freeze, any change to
grammar.md or spec.md needs a decisions.md paragraph citing this
section; typo fixes are exempt. The freeze is held by this process and
by the conformance tests (the fixture tests, the tree-sitter conformance
test and the guide's ladder test), not by a hash pin.
